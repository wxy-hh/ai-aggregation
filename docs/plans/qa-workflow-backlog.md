## `QA-WF-01`：车道升级与宿主适配的发布验收 dogfood

- **证据**：正本第 7 节要求发布 QA 工作流自身时，以干净会话的真实 `/implement` dogfood 验证独立上下文审查真实发生、无独立上下文能力时合法暂停；ADR-0040、ADR-0042 的效果也以下一次真实需求为证据，ADR-0042 之后尚无真实需求完整走完新规则。
- **做法**：下一个真实需求在干净会话中走 `/implement`，凭真实的两份独立审查原文关闭本项；宿主没有独立上下文能力时合法暂停。手动派发的审查者、工具测试与本轮审查都不能冒充。
- **在此之前**：`qa-workflow-lane-host-scan` 交付时只能称「待发布验收」。
- **C8/C9 观察**：两次真实闭环完成了独立子代理原文与凭据，但产物复核发现 Spec 语义失真、计划变更理由失实和视觉目标缩小，不能据此关闭发布验收；C8 还发生配额失败后的同轮重试绕路。ADR-0057 的工具测试、本特性手动双轴审查均不冒充下一次干净会话 dogfood。
- **Phase 3 双对照验收闭环（2026-11-26）**：在 `v2.2`（`07ef09d` → `d463e90` → `9be2aa9`）全量落地后，使用两场全新独立干净会话在隔离 worktree 完成双对照真实 dogfood：
  1. **对照 A（效率轨，`.scratch/tools-workbench-ia-migration-v2-2`，`phase3/control-a`）**：干净复验 `/tools` 迁移，首轮独立双轴关键路径 **5.12 分钟**（Standards 3.25m / Spec 5.12m）、全流程活跃 **32.0 分钟**（较旧基线阶段 6 `239.6 分钟` 降 **86.6%**）、18 对 Rename 压缩 **91.13%**（纯代码 **82.4%**），`gate-acceptance-01` 与 `gate-review-01` 均一次 `PASS`，零工作区踩脏、零编号冲突。
  2. **对照 B（质量防线轨，`.scratch/profile-quick-nav-anchor`，`phase3/control-b`）**：零剧透植入 4 类历史高发变异（移动锚点滚错宿主 / 无语义按钮绑定 / 空白 `VisualTarget` 截图 / 减动效首读错误），`r1` 独立双轴在无提示下 **`4/4` 全部阻断级独立检出**并额外发现 2 条真实 `S-H`，`r2` 全修闭环且 `ego-browser` 真实渲染 `390×844` 截图（`variance=559.4`），四次 `seal` 全部一次通过、`gate-review-01` `PASS`。
  据此本项正式关闭，`v2.2` 正式摘除发布验收暂挂标注（未来再改动 QA 工作流自身时，仍按正本第 7 节执行新一轮发布 dogfood）。

## `QA-WF-02`：审查发现分类统计报告

- **证据**：外部评价建议统计各门禁拦下的真实缺陷；审查轴已有 9 个特性共 203 条特性内唯一编号的原文与分流表，缺少逐条分类。
- **做法**：另起会话；只统计审查轴，机器门禁标「未观测」；单位为特性内唯一编号，跨轮复发另列；类别为实现缺陷、证据缺陷、流程/格式、判断建议、误报、无法判断，另记影响等级；两个子代理互盲全量标注，主代理不先给标签，分歧原样交用户裁决并公布一致率；耗时分三列（qa-run 命令累计时长、基线到末个日志的日历跨度、审查观察窗），均不称人工工时。
- **范围外**：旧格式报告与 agent-kb-loop 列排除清单，不进分母。
- **产物**：`docs/reports/2026-10-31-qa-finding-classification.md`，入库；关键依据内嵌短摘录，`.scratch` 路径只作本机溯源。报告不给删规则的结论。

## `QA-WF-03`：`.scratch/` 备份与清理规则

- **证据**：2026-10-31 时 `.scratch/` 有 44 个特性目录、23 个顶层散落文件，共 213 MB，没有保留期或归档规则；目录不入库，证据与审查原文只存在本机。
- **约束**：`.scratch/` 同时是本地 issue tracker（`docs/agents/issue-tracker.md`），清理不能整目录删除，须保留 spec、issues、map 与交接信息；涉及删除审计材料，须单独与用户对齐。

## `QA-WF-04`：过程脚本中命令行数据存储客户端识别

- **证据**：`agent-kb-loop` 的 3 个过程脚本调用 `redis-cli del` 清除注册限流键；现有扫描不识别 `redis-cli`、`psql`、`mysql`、`mongosh`、`sqlite3`、`prisma db execute` 等命令行直连。
- **暂缓依据**：需设计「提及」与「执行」的判定边界，属于新增一类不可豁免的 FAIL；现存命中脚本已交付，且同一脚本的登录接口与密码字面量已会 FAIL（ADR-0044）。
- **已对齐的方向**：命中应判 FAIL；清理测试环境的操作应移到过程脚本外或改走产品接口。
- **同类缺口**：工作区推导只覆盖直接依赖数据库驱动的包，过程脚本经应用源码间接导入数据库客户端（本仓库有 70 个应用侧非测试文件导入 `@repo/db`）不会被识别。候选做法是禁止过程脚本导入工作区任何包的源码，但需区分「导入」与「读取文件文本」，避免误伤只读 SQL 或 schema 做静态检查的脚本。

## `QA-WF-05`：`qa-check` 门禁输出落盘

- **证据**：`qa-check` 的诊断只打印到终端，`acceptance` 只写对账表；「每道机器门禁拦下了什么」没有数据，`QA-WF-02` 只能统计审查轴。
- **做法候选**：给 `qa-check` 增加日志输出，或约定经 qa-run 运行 `qa-check`。
- **ADR-0057 已实现**：plan/acceptance/review 统一经 qa-run 使用 `gate-plan-*`、`gate-acceptance-*`、`gate-review-*`；新 manifest 检查成功 plan 与当前 tree acceptance 前置日志，review 由外层 qa-run 落盘。C8/C9 的无门禁原件问题不再等待 QA-WF-02；本项仍待本特性独立审查与人工终审，未提前写成完成。

## `QA-WF-06`：转录核验绑定特性或会话

- **证据**：转录核验扫描本仓库全部 Claude 会话，没有绑定特性或会话 ID，可能误报，也可能被其他会话中的相同文本消警（ADR-0044 已知局限）。
- **已实现（ADR-0048），待人工终审**：`collect` 发放一次性 challenge，nonce 进入子代理 prompt 与 `.source.json`；有 challenge 的新轮次按 nonce 精确匹配，不再依赖全局文本碰撞。无 challenge 的旧轮次仍沿用原逻辑。终审通过前不写完成态。
