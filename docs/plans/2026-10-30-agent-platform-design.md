# Agent 应用与运行平台总体设计

> 日期：2026-10-30  
> 状态：已批准，待拆分实施计划  
> 目标周期：6 个月  
> 标杆应用：深度研究助手  

## 1. 背景

当前项目已经具备多模型对话、知识库 RAG、会话记忆、内置工具、用户 Webhook 工具、Human-in-the-loop 写操作审批、配额结算、Langfuse 接缝、BullMQ Worker 和多种 AI 业务页面。

现有能力仍以具体页面和同步请求为主要组织方式。Agent 执行依赖 `/api/chat` 的长连接，运行中状态主要存在于请求内存中，完成态才写入 `AgentRun`。项目尚未形成统一的 Agent 定义、异步可恢复 Runtime、MCP 工具接入、运行事件补拉、上下文压缩、分层记忆、真实模型评测及 AgentOps 控制面。

本设计不另建一个与现有业务割裂的新项目，而是在当前 Monorepo 中渐进建设通用 Agent 平台内核，并用深度研究助手验证平台能力。

## 2. 产品定位

项目对外定位调整为：

> 全栈 Agent 应用与运行平台。支持多模型、RAG、工具治理、异步可恢复执行、人机审批、记忆和 AgentOps，并以内置深度研究助手验证平台能力。

平台同时服务三类使用场景：

1. 普通对话：低延迟、同步流式执行；
2. 知识库问答：带权限和引用的 RAG Agent；
3. 深度研究：异步长任务、计划确认、多源检索、断线恢复和报告产物。

## 3. 目标与非目标

### 3.1 六个月目标

- 建立真实模型 Agent 评测基线和可重复的消融实验；
- 建立生产可用的 Trace、指标、反馈和 Bad Case 回归闭环；
- 实现异步可恢复的 Agent Runtime v2；
- 实现运行状态、Checkpoint、事件补拉、暂停、恢复、取消和重试；
- 将 MCP 工具纳入现有工具治理、审批、审计和成本边界；
- 实现上下文压缩和有治理的分层记忆；
- 建立版本化 Agent Definition 与按需加载的 Skills；
- 以数据判断最小 Multi-Agent 是否有净收益；
- 建立 CI、故障注入和可演示的运行控制面；
- 用同一数据集完成 TypeScript 自研 Runtime 与 Python + LangGraph 的对照实验。

### 3.2 非目标

六个月内不建设：

- 通用可视化拖拽工作流；
- Agent 或 MCP 公共市场；
- 允许普通用户启动任意本地 Stdio MCP Server；
- 自研代码执行沙箱；
- Kubernetes 多集群调度平台；
- 为追求框架统一而重写普通对话链路；
- 没有评测假设支撑的通用 Multi-Agent 框架；
- 与求职目标关联较弱的新图像、视频或命理业务。

## 4. 总体原则

### 4.1 标杆应用驱动平台化

平台内核通过深度研究助手的真实需求产生，不预先抽象一套没有使用方的通用框架。新增能力应至少完成一个纵向业务闭环；出现第二个真实使用方后，再将稳定共性提取到 `packages/agent-*`。

### 4.2 同步与异步 Runtime 并存

- Runtime v1：保留现有 `/api/chat` 同步 SSE，服务普通问答和短任务；
- Runtime v2：新增 BullMQ 驱动的异步执行，服务深度研究和其他长任务；
- 两者共用模型适配、工具契约、工具治理、RAG、配额、Trace 和流事件语义；
- 不强迫所有请求进入队列，避免普通问答承担不必要的排队与持久化开销。

### 4.3 PostgreSQL 是运行事实来源

- PostgreSQL 保存运行状态、Checkpoint、事件、工具执行、审批和产物引用；
- Redis 用于 BullMQ、分布式锁、实时通知和可重建缓存；
- Redis Pub/Sub 不承担历史恢复；
- 对象存储保存大文件、研究报告及其他产物正文；
- Langfuse 保存观测数据，但不作为业务运行状态的事实来源。

### 4.4 安全和计费在模型之外执行

工具权限、参数校验、SSRF 防御、审批、幂等、配额和审计必须由确定性代码保证。Prompt 约束和内容标签不能代替安全边界。

### 4.5 用评测决定功能是否进入主链路

MCP、上下文压缩、记忆、Skills 和 Multi-Agent 均须通过同口径任务集比较质量、成本、延迟和失败率。没有净收益的能力可以保留为实验结果，但不进入默认生产路径。

## 7. 核心领域模型

### 7.1 AgentDefinition

表示用户可运行的 Agent 配置，而不是一次运行实例。

主要字段：

- `id`、`ownerId`、`name`、`description`；
- 应用类型和可见范围；
- 当前发布版本；
- 默认模型、能力包、知识库和工具授权；
- Memory、Context、预算和审批策略；
- 创建、更新时间和软删除状态。

第一阶段只内置系统定义，不急于开放通用无代码编辑器。

### 7.2 AgentVersion

冻结一次可复现的 Agent 配置：

- System Prompt 及其哈希；
- 模型与参数；
- 工具白名单和版本；
- Skill 列表；
- RAG、Memory、Context 策略；
- 最大步骤、Token、工具次数和运行时间；
- 配置 Schema 版本。

每次运行必须绑定版本，避免配置变化后无法复现实验和故障。

### 7.3 AgentRun

一次运行的聚合根：

- `runId`、用户、会话、AgentVersion；
- `mode`：`sync` 或 `async`；
- 状态、当前节点和状态版本；
- 输入摘要、输出摘要、产物引用；
- Trace ID、配额预留和结算状态；
- 创建、启动、暂停、完成和过期时间；
- 失败分类和可恢复性。

### 7.4 RunCheckpoint

保存可恢复的结构化状态：

- `runId`、节点、序号、`stateVersion`；
- 计划、当前步骤、研究笔记、工具结果引用；
- 已消耗预算和剩余预算；
- Memory/Context 引用；
- 恢复游标和创建时间。

Checkpoint 只保存恢复所需状态。大文本和文件使用引用，不把无限增长的正文复制进每个快照。

### 7.5 RunEvent

支持实时展示和断线补拉：

- 每个 `runId` 下单调递增 `seq`；
- 事件类型、结构化载荷、创建时间；
- 可见范围和载荷版本；
- `(runId, seq)` 唯一约束。

客户端首次进入先读取当前快照和最近事件；重连时使用 `afterSeq` 补拉，再切入实时 SSE。

### 7.6 ToolExecution

保存工具执行事实和幂等状态：

- `runId`、节点 ID、模型 Tool Call ID；
- 稳定幂等键；
- 工具来源、名称和版本；
- 脱敏参数哈希；
- `pending/running/succeeded/failed/uncertain`；
- 外部回执、耗时、错误分类和重试次数；
- 审批关联和 Trace Span ID。

只读工具可以按策略重试。写工具只有在上游支持幂等键、能够查询结果或进入人工确认时才允许自动恢复。

### 7.7 ApprovalRequest

在现有 HMAC 一次性审批基础上，增加持久化任务关联：

- `runId`、`toolExecutionId`；
- 请求状态和失效时间；
- 风险摘要、目标、脱敏参数；
- 审批人和审批结果；
- 恢复版本与一次性消费记录。

### 7.8 Artifact

研究报告、图表、文件和导出内容统一为产物：

- 产物类型、版本和 MIME；
- 所属运行、用户和会话；
- 对象存储地址和内容哈希；
- 引用来源与生成节点；
- 是否允许回写知识库。

### 7.9 EvalDataset、EvalRun、EvalResult

- Dataset 冻结任务、成功标准、允许和禁止工具；
- EvalRun 绑定 AgentVersion、模型、Prompt、工具和数据集版本；
- Result 保存逐题原始结果、评分、Trace、成本、延迟和失败分类；
- 汇总指标必须能追溯至逐题记录。

## 8. Runtime v2 状态机

```text
created
  ↓
queued
  ↓
planning
  ↓
waiting_plan_approval ──拒绝──→ cancelled
  ↓确认/调整
running
  ├──→ waiting_tool_approval ──确认──→ running
  ├──→ retryable_failed ──重试──→ queued/running
  ├──→ paused ──恢复──→ queued/running
  ├──→ cancelled
  └──→ synthesizing
             ↓
         completed
```

终态包括：`completed`、`failed`、`cancelled`、`expired`。

要求：

- 状态迁移由统一服务校验，API 和 Worker 不得各写一套规则；
- 每次迁移使用乐观锁或状态版本，防止并发 Resume；
- 进入可恢复状态前先保存 Checkpoint；
- 任务可能重复投递，Worker 必须幂等；
- `waiting_*` 状态不占用 Worker；
- 配额在创建运行时预留，完成时结算，取消或不可恢复失败时释放；
- 长时间挂起任务需要过期和对账策略。

## 9. 深度研究标杆应用闭环

1. 用户在 `/chat` 选择“深度研究”；
2. 选择私有知识库、允许工具、研究深度和预算；
3. Web 创建异步 `AgentRun` 并投递任务；
4. Worker 生成研究计划并保存 Checkpoint；
5. 运行进入计划确认，前端允许修改未执行步骤；
6. 用户确认后以幂等 Resume 恢复；
7. Runtime 执行公开网络、私有知识库和授权 MCP 检索；
8. 每个节点保存研究笔记、引用、预算和 Checkpoint；
9. 前端实时展示计划、来源、工具状态、成本和阶段产物；
10. 页面刷新后使用快照与 `afterSeq` 恢复；
11. 写操作必须进入现有审批链路；
12. 质检节点检查实体覆盖、来源充分性和引用支持；
13. 汇总节点生成带引用报告并保存为 Artifact；
14. 用户可以导出、继续追问或明确选择回写知识库；
15. 评分和问题反馈关联 Trace 与 AgentVersion；
16. Bad Case 进入评测集，修复后执行同口径回归。

## 10. MCP 工具平台

### 10.1 范围

第一版只支持管理员预配置的远程 MCP Server 和受控开发环境连接。普通用户不能提供任意启动命令，也不能让 Web/Worker 运行任意 Stdio 进程。

### 10.2 统一治理

MCP 工具发现后映射为现有 `AgentToolSpec`，必须经过 `ToolRegistry` 和 `ToolExecutionPipeline`：

- 工具命名空间和重名检测；
- JSON Schema/Zod 边界校验；
- 连接与调用超时；
- 权限和 Agent 白名单；
- 只读/写操作风险分类；
- 写操作审批；
- SSRF 与出站网络策略；
- 响应大小和内容截断；
- 调用上限、成本和审计；
- Server 健康状态和熔断。

首批服务应选择一个只读公开信息源和一个受控内部数据源，证明统一协议和权限治理，而不是追求数量。

## 11. Context 与 Memory

### 11.1 上下文组装

每个模型步骤按固定顺序组装：

1. AgentVersion 中的系统约束；
2. 当前任务目标与计划；
3. 当前步骤所需的最小运行状态；
4. 经权限过滤的知识库和 Memory；
5. 最近消息窗口；
6. 压缩后的历史摘要；
7. 必要工具结果引用。

系统应记录各部分 Token 占比，避免只按字符串长度盲目截断。

### 11.2 Context Compaction

触发条件以 Token 预算为准，不只按消息条数。压缩结果应包含：

- 用户目标与硬约束；
- 已确认事实及来源引用；
- 未完成步骤；
- 关键工具结果引用；
- 用户决策和审批结果；
- 不确定项与失败记录。

原始消息仍持久化，摘要只是推理上下文。压缩前后必须用同一任务集比较任务成功率、Token、延迟和引用完整性。

### 11.3 分层记忆

在现有会话片段向量检索上增加：

- 情景记忆：某次运行、选择和结果；
- 语义记忆：相对稳定的用户偏好与事实；
- 记忆候选：模型提出但尚未持久化的内容；
- 记忆治理：来源、置信度、过期、冲突、更新和删除；
- 用户控制：查看、纠正、删除和关闭记忆。

敏感信息默认不写入长期记忆。记忆写入和读取都要有 Trace 与评测。

## 12. Agent Definition 与 Skills

Agent Definition 第一阶段只支持系统内置定义和受控配置，不做拖拽编辑器。

Skill 是按需加载的能力包，至少包含：

- 名称、描述和适用条件；
- Prompt 指令；
- 允许工具与资源；
- 输入/输出契约；
- 版本和测试用例；
- Token 预算。

深度研究首批 Skill：

- 多源事实调研；
- 对比分析；
- 私有知识库核验；
- 带引用报告生成。

只有当按需加载相较全量 Prompt 在质量或成本上有可测收益时，才作为默认路径。

## 13. Multi-Agent 边界

Multi-Agent 只实现一个可证伪的最小模式：

- Supervisor 拆分相互独立的只读研究子任务；
- Researcher 子 Agent 使用隔离的精简上下文并行检索；
- Supervisor 汇总结构化结果，Writer 生成最终报告；
- 子 Agent 继承父运行的总预算、权限和允许工具；
- 子任务有独立 Trace 和 Checkpoint，但归属同一 `AgentRun`；
- 子 Agent 不得自行扩大权限或发起未经批准的写操作；
- 子任务失败时允许局部重试或退化为单 Agent 顺序执行。

是否进入生产由 Single Agent 对照实验决定。简单任务默认不启用 Multi-Agent。

## 14. AgentOps 闭环

### 14.1 Trace

跨 Web、BullMQ 和 Worker 传播：

- `traceId`、`runId`、`conversationId`、`agentVersionId`；
- Planner、模型决策、工具、Checkpoint、审批、Evaluator、Writer、结算分别形成 Span/Generation；
- Usage 标记 `actual/estimated/missing`；
- 密钥、Token、Webhook 凭证、个人隐私和不必要的知识正文必须脱敏。

### 14.2 Eval

任务集至少覆盖：

- 普通问答；
- 单步和多步公开检索；
- 私有知识库问答；
- 公私资料联合研究；
- 工具超时、参数错误和重复调用；
- 无答案拒答；
- 恶意网页和文档提示注入；
- 写操作审批；
- 中途取消、断线、Worker 重启和重复投递；
- 长上下文压缩；
- Memory 使用与冲突；
- Single 与 Multi-Agent 对照。

指标包括任务成功率、工具选择与参数正确率、引用正确率与覆盖率、异常收敛率、恢复成功率、重复副作用次数、Token、成本和延迟。

### 14.3 Feedback 与 Bad Case

- 用户点赞、点踩和问题反馈绑定 `runId` 和 Trace；
- 失败运行可以一键标记为候选 Eval Case；
- 人工补充成功标准后进入版本化数据集；
- 每次 AgentVersion 发布前跑固定回归集；
- 报告保留逐题原始结果和配置版本，不只保存汇总分数。

## 15. 控制面功能清单

### 15.1 用户侧

- `/chat` 深度研究模式；
- 研究配置：深度、知识库、工具、预算；
- 计划确认与修改；
- 实时阶段、来源、成本和错误展示；
- 刷新与断线恢复；
- 暂停、恢复、取消和安全重试；
- 待审批卡片与审批历史；
- 研究报告查看、导出、追问和回写知识库；
- Memory 查看、纠正和删除；
- 运行反馈。

### 15.2 管理与开发者侧

- AgentDefinition 与版本列表；
- MCP Server 配置、授权和健康检查；
- 工具权限、风险等级和调用审计；
- 运行中心：运行中、等待审批、失败、已完成；
- 运行详情：事件、Checkpoint、Trace 和产物；
- Eval 数据集、运行、版本对比和逐题详情；
- 成本、延迟、工具错误和恢复指标；
- Bad Case 归档与回归状态。

## 16. API 与事件原则

建议的资源接口，不在本设计中冻结具体 URL：

- 创建和查询 AgentRun；
- 暂停、恢复、取消和重试；
- 获取快照和按序号补拉事件；
- SSE 实时订阅；
- 计划确认与调整；
- 工具审批；
- AgentDefinition 和版本；
- MCP Server 与工具授权；
- Eval Dataset、EvalRun 和结果；
- Memory 管理；
- Artifact 查看、导出和回写。

事件协议应复用现有聊天流契约中的稳定语义，并增加 `runId`、`seq`、`eventVersion` 和恢复所需事件。不得为 Web、Worker 和前端维护三套不一致的事件类型。

## 17. 可靠性与安全

必须验证以下故障窗口：

- Job 重复投递；
- Worker 在工具执行前崩溃；
- 只读工具成功后、Checkpoint 前崩溃；
- 写工具外部成功、本地未确认时崩溃；
- Checkpoint 成功、实时事件未广播；
- 客户端断线和事件遗漏；
- 多个 Resume 并发；
- 审批凭证重复使用或过期；
- 配额预留成功但任务未入队；
- 任务完成但结算暂时失败；
- MCP Server 超时、重名、越权和响应过大；
- 恶意知识文档或网页诱导调用高权限工具。

不可确认的外部写操作进入 `uncertain` 并要求人工处理，不得自动重放。

## 18. 包边界演进

第一阶段不立即创建多个新包。先在当前链路形成稳定接口：

1. 在 `packages/shared` 放置跨端运行状态和事件 Schema；
2. 在 `packages/db` 和 `packages/queue` 实现持久化与任务契约；
3. Runtime v2 初期可以在 `apps/worker` 内形成清晰模块；
4. Tool Registry/Pipeline 暂时保留现有位置，通过依赖倒置减少 app 层耦合；
5. 当同步对话与异步深度研究或第二个异步应用共同使用同一能力后，再评估提取：
   - `packages/agent-core`：领域契约和状态机；
   - `packages/agent-runtime`：与框架无关的执行接口；
   - `packages/agent-evals`：评测契约和指标。

提取标准是出现真实复用和稳定边界，不以目录看起来像平台为目标。

## 19. Python + LangGraph 对照实验

对照实验放在同一仓库的 `experiments/langgraph-research-baseline/`，不进入主生产链路。

要求：

- Python、FastAPI、Pydantic、asyncio、LangGraph、pytest；
- 使用与 TypeScript Runtime 相同的任务数据集和成功标准；
- 实现最小规划、工具、Checkpoint 和恢复；
- 对比质量、Token、延迟、恢复行为、开发量和维护复杂度；
- 记录 LangGraph 带来的收益和仍需业务层解决的问题；
- 不维护第二套用户、计费、工具权限和生产控制面。

## 20. 六个月里程碑

### M0：事实口径与真实基线，2 周

- 修正文档与代码口径；
- 冻结 20～30 个真实任务及成功标准；
- 真实模型运行并保留原始结果；
- 完成规划/质检消融；
- 打通完整 Trace 和脱敏；
- 产出基线与 Bad Case 报告。

### M1：异步 Runtime v2 最小闭环，5～6 周

- AgentRun、Checkpoint、RunEvent、ToolExecution 数据模型；
- 创建、入队、Worker 消费和状态机；
- 快照、事件补拉和 SSE；
- 深度研究计划确认、执行和报告产物；
- 配额、Trace 和现有工具接入；
- 页面刷新、断网和 Worker 重启恢复；
- 重复投递与副作用幂等测试。

### M2：MCP 工具平台，2～3 周

- 管理员配置和健康检查；
- 工具发现、命名空间和 Schema 映射；
- 统一管道治理、授权、审批和审计；
- 两个受控 MCP Server 演示；
- 超时、越权、重名和断连测试。

### M3：Context 与 Memory，3～4 周

- Token 驱动的上下文组装和压缩；
- 压缩前后对照实验；
- 情景/语义记忆、候选写入和治理；
- 用户记忆管理；
- 记忆准确性、冲突和隐私测试。

### M4：Agent Definition、Version 与 Skills，3 周

- 系统内置 AgentDefinition；
- 版本冻结和运行绑定；
- Skill 格式、加载策略和首批研究 Skills；
- 版本比较与回滚；
- 按需加载对照实验。

### M5：受控 Multi-Agent，3～4 周

- Supervisor 和只读 Researcher；
- 并行子任务、预算继承和上下文隔离；
- 局部失败和单 Agent 降级；
- 同数据集重复对照；
- 根据净收益决定是否默认启用。

### M6：AgentOps、CI 与求职证据，3～4 周

- 运行中心、Eval 控制面和 Bad Case 回流；
- CI 中运行 lint、typecheck、测试和关键 QA 门禁；
- 故障注入、恢复和容量测试；
- Python + LangGraph 对照实验；
- 架构图、演示脚本、指标报告和简历表述；
- 核对所有表述均可由源码、Trace、测试或原始实验支持。

## 21. 阶段门禁

每个里程碑进入下一阶段前必须满足：

- 用户闭环可以真实操作；
- 单元、集成和必要 E2E 测试通过；
- 核心链路完成真实浏览器验收并保存证据；
- Trace 能解释成功和失败路径；
- 配额、权限和多租户边界经过验证；
- 指标保留原始数据和版本；
- 失败场景有明确状态和恢复行为；
- 文档不将计划、模拟或 mock 结果表述为生产能力；
- 标准/慢车道完成项目规定的 QA 和独立审查门禁。

## 22. 成功标准

六个月后，项目至少应能现场演示：

1. 普通对话继续以低延迟同步流运行；
2. 深度研究任务进入后台执行，刷新和断网后可以恢复；
3. 计划与写操作分别支持持久化 Human-in-the-loop；
4. 内置、Webhook 和 MCP 工具都经过统一治理；
5. 报告同时使用公开来源和用户私有知识库，并提供可核验引用；
6. 长上下文经过可解释压缩，用户可以管理长期记忆；
7. 任一运行都能定位 Trace、版本、成本、事件和 Checkpoint；
8. Bad Case 可以转为 Eval Case，并对两个 AgentVersion 做同口径比较；
9. Worker 重启、重复投递和并发恢复不会导致已知写操作重复执行；
10. 能用真实数据解释 Single/Multi-Agent、自研 TS/LangGraph Python、压缩前后和 Skills 加载前后的取舍。

## 23. 首个实施切片

设计批准后的第一个实施切片不是 MCP 或 Multi-Agent，而是：

> 修正事实口径，建立真实 Agent Eval 基线，并打通一条可追溯的完整 Trace。

该切片提供后续所有架构改造的比较基准。完成后再进入 Runtime v2 的数据模型和最小异步纵向切片。
