## 一、先回答最关心的问题

| 问题 | 结论 | 关键证据 |
| --- | --- | --- |
| 是不是审查准确率太低，所以耗时、复审多？ | **不是主要矛盾。** 原文中的多数发现有一手代码或证据依据，但“事实成立”不等于“都应阻断交付”。真正突出的问题是发现分类、严重度一致性、编号管理和修复决策失真。没有独立标注的全量真值集，不能严谨地宣称“100% 准确”。 | 直接产品缺陷、规范问题、测试/证据问题和流程新鲜度问题被混在同一复审轨道；r2 与 r3 还复用了不同语义的 `P-M5`。 |
| 是不是检查内容太多？ | **是核心原因之一，而且负荷在规划期就被放大，在复审期又被重复计算。** 40 条断言全部 `required`，37 条为 P0，26 条 browser；首轮和每轮复审都要求逐行响应。搬家 Diff 达 577,166 B。 | `.scratch/tools-workbench-ia-migration/_qa/spec-review-checklist.json`；`tooling/scripts/qa-spec-review.mjs:48-54`。 |
| 为什么复审次数这么多？ | **不是单纯因为缺陷多，而是六类放大器串联：可变审查对象、无效包仍派发、每轮全量重审、修复捆绑且未先证伪、门禁终态矛盾、429 与浏览器基础设施失败。** | r1/r2/r4 均有审查期间继续改文件；Spec r1–r3 全部 seal 失败；r3 上限后仍派 r4/r4b；r4 两轴无有效返回。 |
| 四小时是否都是模型在审查？ | **不是。** Gemini 所列约 240 分钟是“审查 + 修复 + 重验 + 工具调试 + 等待”的阶段 6 总账，不能全记到审查模型头上。有效子代理 837 次工具调用中，Spec 轴占 597 次，且 66 次 Read 耗在排查工具脚本的 seal 失败。 | 主会话与子代理 JSONL；`review/r{1,2,3}-spec-axis.md`。 |

**一句话根因**：当前流程优化的是“每一轮表格和凭据是否齐全”，而不是“用最少重复工作降低真实交付风险”。审查对象、证据身份和工作继承没有先建模，后续只能用更多模型调用、更多门禁和更多轮次补偿。

### 建议立即拍板的目标形态

1. **r1 全量双轴，默认最多一次自动增量复审 r2**；r2 仍有真实阻断则进入 `WAITING_HUMAN`，不自动进入 r3/r4。该变化需 ADR 修订现有“r2、r3 两轮上限”。
2. **审查期间冻结审查对象，双轴都到达终态后才能修复**；文档、spec、scope、QA 产物同样冻结。
3. **无效审查包在派发前失败，配额/工具失败立即暂停**；禁止“直到 seal 成功”的无限重试。
4. **完整覆盖清单保留，语义核验按脚本/测试文件分组，未变化证据按哈希继承**；不再每轮重填 40 行。
5. **默认可自动修真实阻断项，S-J 清理与主修复分开**；但不能把所有 S-J 机械视为审美建议。
6. **r1 双轴保留**。增量复审是否只需单轴，继续遵循 ADR-0054 的变化类型规则，不借本次提速暗中取消独立审查。

## 二、证据、口径与当前真实结局

### 2.1 证据可信度分层

本诊断按以下优先级使用材料：

1. **一手产物**：六份审查原文、三份 Standards 凭据、`review-report.md`、`_qa/`、137 份 evidence 日志、截图、主会话与 11 份子代理 JSONL。
2. **会话导出**：`.scratch/tools-workbench-ia-migration/2026-11-26-112209-local-command-caveatthe-command-below-was-run-d.txt`，用于定位实际操作顺序。
3. **二手复盘**：`retro-evidence.md`，只作索引，不直接采信其遗漏或时间判断。
4. **Gemini 草案**：保留其实证主体，逐项修正下述口径和方案副作用。

当前主会话 JSONL 已增长到 5,515 行；`retro-evidence.md` 的 5,332 行是较早快照。两者不矛盾，混用行号才会矛盾。

### 2.2 时间账必须分成四种

| 口径 | 本文采用的事实 | 不能怎样解读 |
| --- | --- | --- |
| 阶段 6 主会话活跃账 | Gemini 以 30 分钟间隔剔除长中断后，估算约 **239.6 分钟**；本文复算因分段边界略有差异，但不改变“约 4 小时”的量级。 | 不能称为“纯 code-review 推理耗时”。其中含修复、浏览器重验、门禁调试和等待。 |
| 审查子代理活跃账 | 有效 r1b/r2/r3 六轴合计约 **82.3 分钟、837 次 tool_use**；Spec 为 597 次。 | 各轴并行，不能把求和当用户墙钟；不同停顿阈值也会得到不同“活跃”分钟数。 |
| 初次 r1 用户等待 | 两个 Opus 子代理转录首末均跨越约 **28–30 分钟**，只有 20/24 次工具调用，无原文产出，且反复 429。 | 不能只写“idle”或只引用约 6 分钟的剔除停顿口径，隐去用户实际等待。 |
| 命令执行账 | 浏览器单轮通常几十秒，Vitest 多数数秒；真正昂贵的是反复重跑、70 秒限流等待、截图/登录/端口排障。 | 不能把 4 小时解释成测试命令本身慢。 |

后续工具必须直接记录 `review_wait / reviewer_active / repair / acceptance / seal_retry / quota_wait`，不再靠复盘者选择 60 秒、5 分钟或 30 分钟间隔猜耗时。

### 2.3 这次特性并未形成成功的终审闭环

- Spec r1/r2/r3 均无 `.source.json`；Standards 三轮有凭据。
- r4 两轴与 r4b 均因配额失败，没有有效审查原文。
- `review/r2-spec-axis.md:44-51` 的失鲜问题与 `review/r3-spec-axis.md:49-54` 的截图问题都使用 `P-M5`，最终台账无法清晰表达两者各自闭环。
- `review-report.md:1` 声称两轴均由 `code-review` 技能派发并封存，但 r2/r3/r4 实际由主代理直接派 Agent，Spec 也未封存；自述不能当证据。
- 唯一 `evidence/gate-review-01.log:135-139` 为 FAIL，之后没有一份成功的最终 `gate-review` 证据。

因此，本次只能作为**失败 dogfood 样本**，不能作为“业务已完整交付、流程已验证”的成功案例。

## 三、对“准确率”的重新审计

### 3.1 不是 18 个干净、唯一的发现

按原文语义而不是最终表格行数重新梳理：

| 轴 | 原文中的发现 | 语义数量与问题 |
| --- | --- | --- |
| Standards | S-H1～S-H3、S-J1～S-J8 | **11 个编号**。S-J8 把真实生命周期/竞态缺陷与 Duplicated Code 混在一个“判断建议”中，分类不准确。 |
| Spec | r1 的 P-W1/P-W2/P-M1～P-M4；r2 新增 P-M5（审查包失鲜）、P-M6（截图与弱验收）；r3 又把截图问题命名为 P-M5 | **按语义至少 8 类问题**；r2 的失鲜 P-M5 未进最终表，P-M6 也未进表，r3 的 P-M5 与 r2 冲突。 |

所以，Gemini 的“18 条唯一编号 + P-M6 并入 P-M5、Standards 10 条”在计数与语义上都不严谨。**至少 19 类语义发现、18 行最终分流、一个编号被不同问题复用**，才是这组产物反映的真实状态。

编号冲突不是小事：复审、分流、证据绑定和人工终审都以编号为主键。主键不稳定，后续所有自动化都会做无用功或对错对象。

### 3.2 应同时衡量三种“准确率”，而不是只看发现是否属实

1. **事实精度**：代码、规范、日志是否支持这条陈述。此次多数核心发现有依据，Gemini 对这一点的判断基本成立。
2. **处置精度**：是否把产品 Bug、规范硬违规、测试缺口、证据失效、流程失鲜和纯建议分到正确轨道。此次明显较差。
3. **跨轮一致性**：同一问题是否在首次出现时就被赋予稳定编号和严重度，后续是否持续追踪。此次较差。

典型反例：

- `P-W1` 的移动锚点失效、`S-H3` 的减动效时序、`S-J8` 中的卸载/竞态问题，属于真实代码行为或生命周期风险，值得阻断和复审。
- `P-W2` 主要是验收断言与 `<button>` 实现形态不匹配，不是用户功能本身坏了；`P-M1～P-M4` 主要是测试覆盖、绑定与证据有效性；r2 `P-M5` 是流程失鲜。它们不能全部被称为“真实产品漏洞”。
- 截图问题在 r1 已见空白/切头，r1 只写补充说明；r2 定为 `P-M6`；r3 又以新的 `P-M5` 定为阻断。不是事实突然变化，而是首次定级与编号管理失效。
- `S-J6` 不能简单贬为“审美洁癖”。`DESIGN.md:153-158` 明确禁止 `white/45` 野值、要求 `backdrop-saturate-150` 和玻璃后有色可磨。真正的问题是它为何被放进 S-J、为何实现方先驳回、为何补丁未经浏览器验证又产生层叠错误。

**结论**：此次不是“模型总是幻觉所以慢”，而是“高事实价值的发现，被不稳定的分类、主键和修复流程放大成高成本”。

## 四、第一性原理：应该优化什么

QA 的第一性目标不是表格完整、轮次越少越好或门禁 PASS，而是：

> 在独立审查与核心链路证据不可缺席的前提下，最小化“漏出真实缺陷的预期成本 + 验证成本 + 人与配额的等待成本”。

阶段 6 的用户感知成本可拆为：

```text
T总 = T打包/预检
    + T首轮双轴关键路径
    + T分流
    + Σ(每轮 T修复 + T受影响重验 + T增量复审)
    + T工具/配额等待
```

当前系统的错误等价于让每一轮都执行：

```text
全量 Diff + 全量规范 + 全量 40 行对账 + 全量截图 + 全部待复核编号
```

正确的复审工作量应是：

```text
未闭环编号
+ 自上次已审快照后变化的文件/证据
+ 受这些变化影响的依赖断言
+ 必要的历史上下文（按需读取，而非默认全量重读）
```

**覆盖全集不等于每轮工作全集。** 40 条断言都可以持续可追踪，但 unchanged 的行应该由机器继承，而不是让模型再次证明它已经证明过的事实。

## 五、根因链：Gemini 抓住了什么，还缺了什么

### 根因 1：审查对象不是不可变快照，主代理反复踩脏进行中的审查

这是比“r2 一次抢跑”更系统的问题：

- r1 派发后，主代理修改 `GLOSSARY.md` 与 spec（会话导出 `:6350`、`:6375`），使原 challenge 失效；随后将 r1 无产出简单归为 idle 并重派 r1b。
- r2 Standards 已返回而 Spec 仍在运行时，主代理修改三个白名单文件（会话导出 `:8408-8452`），r2 Spec 随后报 `treeDigest` 不一致。
- r4 派发后，主代理又修改 spec 的 Out of Scope（会话导出 `:14831`、`:14860`）。

Gemini 只完整指出了 r2，漏掉 r1 和 r4 的同类行为。根因是审查者同时读取静态 Diff 与**仍在变化的 live 工作区**，而主代理把等待时间当继续做任务的空档。

### 根因 2：无效包没有在派发前失败，seal 错误又被提示为无限重试

Gemini 对“三轮 Spec seal 全失败、66 次 tooling Read”的方向判断正确，但源码机制需要精确修正：

- `qa-check.mjs:482-511` 已有引用闭包解析，不是完全“只看 argv”。
- 真正缺口是 `scriptReferenceTargets`（`qa-check.mjs:464-470`）只接受 `$DIR/`、`${DIR}/` 或绝对路径重定向；原包装器使用 `SCRIPT_DIR + BROWSER_SCRIPT`，无法解析到真实 `.browser.mjs`。
- 于是 `sourceCandidates` 只留下 `.sh`；`qa-spec-review.mjs:241-253` 又要求候选路径中存在 ±5 行真实谓词，形成结构性不可封存。
- prompt 要求“修正后重试，直到打印 QA_REVIEW_RECEIPT”，把**包生成错误**误当成**审查者可在原文中修复的错误**，直接诱导 r2 Spec 308 次调用。

最终通过把真实脚本路径额外塞进 argv 绕过，并未修复解析与错误路由。

### 根因 3：Coverage v2 只减少表格列，没有减少语义核验工作

- 40/40 `required`，37 条 P0、3 条 P1；26 browser、2 integration、12 unit。
- `isRequiredSpecRow` 将 changed、browser/api、非 PASS、P0 全部纳入，规则本身如预期工作；失灵的是上游风险标级和下游没有分组/继承。
- 58 条 US 中，大量是未改后端与治理行为的“保持能力”条目，却被展开成新追踪与人工核验负担。
- 初始规划用了 5 条 browser TC，后续增到 6 条、7 份脚本；规划报告以“正好卡在 5 条上限”为优点，忽略 `qa-test-planner/SKILL.md:62` 的**默认 1–3 条核心主链路**。这是在填额度，不是在控制成本。

Gemini 提出“required 压到 40%”仍是在优化计数，容易诱发删覆盖。正确指标应是**重复核验单元数、每个高风险行为的有效覆盖率和增量继承率**。

### 根因 4：没有内容寻址的证据身份与增量继承

- `review-package.diff` 为 577,166 B、13,531 行；18 个迁移组件/测试以删除+新增展开，缺少 rename 视图。
- r2/r3 虽叫增量复审，Spec 仍重填完整 40 行，截图、脚本、测试和规范被重复读取。
- 同一截图、同一绑定、同一脚本只要内容未变，就应能沿用上轮语义结论；现在没有 `sourceHash / evidenceHash / verifiedHash / inheritedFrom` 这类继承依据。

只生成 `delta.diff` 还不够。没有内容哈希，无法知道哪条旧结论可继承；只看 delta，又可能漏掉修复与旧代码的交互。

### 根因 5：编号、分类和严重度没有单一事实源

- r2/r3 `P-M5` 冲突，r2 `P-M6` 漏出最终表，直接证明“主代理在 prompt 里手写下一个编号”不可靠。
- r3 prompt 明明给了历次 r1/r2 原文，却仍写“新发现从 P-M5 起”，说明派发器没有扫描并保留历史编号空间。
- S-J8 混合真实生命周期 Bug 与重复代码建议；截图问题跨轮严重度变化；S-J6 的规范强度也有争议。
- `rawIndex`（`qa-check.mjs:1915-1928`）只保留编号最后出现位置，不检测同一编号跨轮变成另一个问题。

Gemini 的“机器硬锁所有 S-J/P-X 不进复审”会制造新问题：已被团队明确接受修复的 S-J 也需要验证；真实 Bug 被错标为 S-J 时，硬锁只会把问题藏起来。

### 根因 6：修复策略本身制造了新缺陷与重验税

- r1 后一次性修约 14 项，把真实锚点 Bug、样式清理、字体、共享常量、测试绑定和视觉配方捆在一起，扩大了 blast radius。
- P-W1 经历四次修法才稳定；P-M4 在审查者已指出无点击场景可用 `mobile: true` 后，仍连续两轮保留 `mobile: false`。这些是修复执行问题，不是审查误报。
- 新补丁又引入 S-H3、S-J8 和 S-J6 的层叠问题。审查在 r2/r3 抓出这些问题属于有效工作，不能简单视为“复审找茬”。
- 16 次 acceptance 门禁实际为 **7 PASS / 9 FAIL**，不是 Gemini 写的 8 次失败。失败主要是绑定缺失、证据失鲜、计划变更未记录等本可前移的问题。

### 根因 7：轮次与失败终态相互矛盾，代理被门禁重新推回循环

`qa-workflow.md:152` 规定 r3 后停止，`qa-check.mjs:1874-1894` 又要求本次修编号必须出现在后一轮且未解决保持 BLOCKED。主会话先明确决定“不派 r4”，随后又为了确认修复而派 r4/r4b（会话导出 `:13518-13546`、`:14457-14461`）。

这说明问题不是代理“不懂规则”这么简单，而是流程只提供两个可见结果：

1. 再审查一轮，争取 PASS；
2. 保持 BLOCKED，但没有清晰、可执行的终态交接。

`WAITING_HUMAN` 必须成为正式终态：机器仍不签发交付 PASS，但代理必须停止修复/复审，并输出未闭环编号、已有证据、风险与人工可选动作。单纯把上限从 r3 改成 r2，不补这个终态，只会更早进入同一种矛盾。

### 根因 8：浏览器、配额和宿主流程是放大器，不应与模型审查混为一谈

- Antigravity 429 造成首轮长时间无产出及 r4/r4b 失败；主代理还违规自动换模型重派。
- r2/r3/r4 未通过 Skill 调用 `code-review`，与项目明确规则冲突。
- `ego-browser` 的移动点击、433px 最小宽度、截图 clip、真实接口 30 次/60 秒限流、登录失效和端口漂移，反复污染验收。
- 当前截图修复依赖 macOS `sips`，非 macOS 仍回退到有问题的 clip；这不是跨平台根治。

这些事项需要独立工作流修复，不能指望换一个“更聪明审查模型”解决。

## 六、对 Gemini 方案的采纳、修正与否决

| Gemini 项 | 本文结论 | 必要修正 |
| --- | --- | --- |
| CR-1 sourceCandidates + 预检 | **采纳，列最高优先级** | 精确修复 `SCRIPT_DIR/BROWSER_SCRIPT` 闭包缺口；优先让 `qa-run` 原生声明 executor，消灭双脚本包装。预检失败不得派 Agent。增加错误分类与有限重试。 |

## 七、v2.2 目标设计与工作项

### P0-1：不可变审查快照 + 双轴终态屏障

**改动对象**：`review-package.mjs`、`code-review/SKILL.md`、`implement/SKILL.md`、`qa-workflow.md`。

- `collect` 为每轮生成不可变 manifest，记录代码、spec、scope、脚本、日志、截图和计划的内容哈希；审查引用在快照上校验，而不是读取随时变化的 live 文件。
- 快照至少覆盖 changed files、审查所需测试/脚本与 QA 产物。可用内容寻址文件存储避免复制整个仓库。
- 主代理在双轴都处于 `returned / failed / cancelled` 前，不得修改任何审查输入，包括“顺手补术语”“更新 spec”“重跑后改写执行记录”。
- 一方先回只读其结果，不开修；两方终态后才进入 triage。
- 如果 live 工作区已变，旧审查只能标记为 `SUPERSEDED`，不得在修复后冒充对当前代码的审查。

**验收**：重放 r1 改 GLOSSARY、r2 改三个文件、r4 改 spec 三类事件，均在修复阶段前被屏障拦截；审查引用不受 live 文件后续写入影响。

### P0-2：可封存性预检 + 类型化错误 + 有限重试

**改动对象**：`qa-run.mjs`、`qa-check.mjs`、`qa-spec-review.mjs`、`qa-preflight.mjs`、`review-package.mjs`。

- 首选增加明确的 executor 契约，例如由 `qa-run` 记录并执行“真实 browser 脚本 + ego-browser executor”，日志天然包含真实脚本路径，淘汰 `.sh + .browser.mjs` 双文件。
- 过渡期复用 `referencedProcessScripts`，补全 `SCRIPT_DIR` 常量与 `BROWSER_SCRIPT` 赋值解析；不能继续要求调用方把同一路径在 argv 里重复传一次。
- `collect` 前验证：候选文件存在、至少一个候选有真实谓词、checklist 与 skeleton 同源、acceptance 与 QA 哈希新鲜。失败在秒级返回，不派审查者。
- 错误只分三类：
  - `REVIEWER_EDITABLE`：引用行或表格可由审查者修正，同轮最多一次 seal 重试；
  - `PACKAGE_INVALID`：sourceCandidates、失鲜、快照缺文件，审查者停止，主代理重建包；
  - `INFRA_UNAVAILABLE`：429、模型别名、宿主失败，保留现场并等待用户，不换模型、不自动重派。
- 删除 prompt 中“直到 seal 成功”的无限循环措辞。

**验收**：原始包装器 fixture 能解析真实 `.browser.mjs`；无有效候选时 2 秒内失败且派发计数为 0；`PACKAGE_INVALID` 不发生 38 次 tooling Read 和反复 seal。

### P0-3：从“断言行清单”升级为“分组审查工作单 + 哈希继承”

**改动对象**：`qa-spec-review.mjs`、`qa-check.mjs`、`code-review/SKILL.md`、对应测试。

保留现有 40 行覆盖清单，新增 `reviewUnits`：

```json
{
  "unitId": "script:tc03-tools-anchors@<sha256>",
  "rowIds": ["TC03-1", "TC03-2", "TC03-3", "TC03-4"],
  "riskReason": ["browser", "changed", "new-behavior"],
  "sourceHash": "...",
  "evidenceHash": "...",
  "verificationStatus": "required | inherited | sampled"
}
```

- browser/api 按过程脚本分组，一个脚本的多条断言一次读取、一次谓词评价，但 `rowIds` 全保留，不能漏覆盖。
- unit/integration 按测试文件和叶子用例分组；新建/改绑定/改源码/非 PASS/核心高风险项必须语义核验。
- 未改源码、未改测试、仅迁移路径且 acceptance 已验证叶子与 exit 0 的存量回归，以机器核验 + 风险抽检为主，不再每轮逐行重读。
- r2+ 仅当 `sourceHash`、对应证据哈希及计划断言语义均未变时继承上轮结论；任一变化只使受影响 unit 失效。
- `required` 不再等于“每轮必须重新人工读一遍”，而是“本轮必须有有效核验状态”，继承也算有效状态。

**验收**：40 行仍全部可追踪；同脚本不重复读取；r2 unchanged 行重写数为 0；修改一个脚本只失效其 rowIds 与依赖项；安全/权限/计费核心行为覆盖不被抽样规则删除。

### P0-4：Rename 感知全量包 + 上轮快照增量包

**改动对象**：`review-package.mjs`。

- 对 prechange 删除与当前新增文件做相似度匹配，输出 `rename from/to + 真实 hunk`，并保留相似度与映射清单。
- 全量包仍是事实基线；另生成上一轮已审快照到当前快照的 `delta.diff`，而不是相对任意工作区状态猜增量。
- `review-brief.md` 只列迁移映射、实质改动文件、受影响规范与本轮 review units，不复制整份 DESIGN。
- 复审默认读取 pending IDs、delta 与 brief；需要理解交互时可读取全量基线，不把“只看 delta”变成新的漏检规则。

**验收**：同一迁移 fixture 的 Diff 体积目标下降至少 80%，rename 前后内容可完整重建；功能修改不会因 rename 折叠消失；r2 不默认读取 577 KB 全量包。

### P0-5：稳定编号登记器 + 发现分类 + 自动对账骨架

**改动对象**：`qa-spec-review.mjs`、`qa-check.mjs`、`review-package.mjs`、`code-review/SKILL.md`。

- 每轴从**所有历史原文（含未 seal）**保留编号空间，工具计算下一编号，主代理不得手写“从 P-M5 起”。
- 同一编号允许表示同一问题的“已修/未修/修错”轨迹，不允许跨轮变成不同问题；发现冲突报 `FINDING_ID_COLLISION`。
- 增加发现元数据：`product_behavior / spec_compliance / test_oracle / visual_evidence / process_freshness / maintainability`。现有 S-H/S-J/P-M/P-W 可暂时保留兼容，但不能继续混装不同语义。
- 生命周期、竞态等真实行为缺陷不得藏在 Fowler S-J；Duplicated Code 部分另立维护性建议。
- 截图仅在图像内容哈希、VisualTarget 与关联断言语义均未变时继承审查结论：未拍到 VisualTarget 是验收证据无效，应在 collect 前阻断；拍到同一目标但构图欠佳不自动升级产品 Bug。
- 自动生成 review-report，所有未闭环项（包括流程失鲜）都有轨迹，杜绝 P-M5/P-M6 漏项。

**验收**：重放当前 r1～r3，工具要求 r3 截图新发现使用 `P-M7` 或继续追踪 `P-M6`，禁止复用 r2 的失鲜 `P-M5`；最终表不再靠人工补漏。

### P0-6：分流后修复 + 正式终态 + 有预算的复审

**改动对象**：`code-review/SKILL.md`、`implement/SKILL.md`、`qa-check.mjs`、`qa-workflow.md`、新 ADR。

- 先分流再动码。默认优先真实阻断项；可维护性 S-J 不与核心 Bug 捆成一批，必要时转专项。
- 产品行为修复先写能证明旧实现失败的测试，再实施最小修复；只重跑受影响证据。不得为通过审查顺手改无关视觉与共享常量。
- 推荐状态机：`COLLECTED → REVIEWING → TRIAGE → FIXING → VERIFYING → REREVIEWING → READY_FOR_HUMAN`。
- 另有三个明确暂停终态：`PACKAGE_INVALID`、`WAITING_INFRA`、`WAITING_HUMAN`。它们都不是交付 PASS，但都必须让 Agent 停止自动工作。
- 默认 r1 + 一次自动 r2。r2 仍有阻断时输出人工决策包：未闭环编号、最后审查原文、修复证据、剩余风险、可选动作（接受风险/授权追加轮/外部独立审查）。
- 轮次上限是防失控护栏，不是“必须一轮通过”的绩效指标。真实复杂缺陷允许由人工授权追加，不得为了达标少报问题。

**验收**：到达上限后无 r3/r4 自动派发；429 后无换模型与 r1b/r4b；主代理不再以“这是确认修复不是复审”为由绕过上限。

### P0-7：把规划与浏览器成本前移收敛

**改动对象**：`qa-test-planner/SKILL.md`、spec 生成规则、`qa-browser-helper.mjs`、浏览器脚本规范。

- 未改业务行为写成“保持契约 + 既有回归测试集合”，不要为每个既有能力重新创造一条高优 US 和人工审查义务。
- P0 只标安全、权限、计费、核心主链路与不可恢复风险；一般文案、排序、可达性与存量回归不得默认全 P0。
- 默认 1–3 条核心 browser journey；TC10 这类纯前端认证引导可下沉组件测试，不能为了用满 5 条上限而保留浏览器。
- 15 分钟时间盒是停止排障/调整接缝的信号，不是可无限延长后仍宣称达标的文案。
- 需要精确 390px 且含真实点击时使用原生 Playwright；需复用桌面登录态时才使用 ego-browser。
- 截图优先原生元素截图，或使用跨平台 PNG 库做视口裁剪；禁止把非 macOS 继续留在已知错误的 clip 路径。
- 真实限流通过减少页面加载、串行验收、固定且可清理的 QA 夹具解决，不为验收关闭生产限流，不用响应注入冒充真实主链路。

### P1：记录真实成本与来源，替代复盘猜测

**改动对象**：审查 dispatch/seal 产物与 retro 聚合。

每轮记录机器可读的：

- nonce、round、axis、快照哈希、dispatch/start/end、终态与失败类别；
- seal 尝试次数、首次失败原因、无效包原因；
- reviewer 工具调用数（宿主可得时）、Diff 字节数、review unit 数、继承数、实际新核验数；
- 主代理修复开始/结束、每类验收重跑时间、429/浏览器等待时间。

这能直接回答“时间到底花在模型、工具、修复还是等待”，避免再产生多套互相矛盾的活跃分钟口径。

## 八、实施顺序：不要一次性重写整个 QA 系统

| 批次 | 内容 | 先解决什么 | 完成条件 |
| --- | --- | --- | --- |
| **Batch 0：行为止血，可先改规范** | 冻结屏障、双轴终态后才修、429/上限立即停止、先分流后修、browser 默认 1–3 条、禁止直接 Agent 派审查 | 不再人为制造 r1b/r4/r4b 和大捆绑修复 | 用当前失败会话做规则走查，所有违规点都有明确替代动作 |
| **Batch 1：正确性修复** | P0-1 快照、P0-2 预检/错误分类、P0-5 编号登记器 | 无效包不派、审查不踩脏、编号不冲突、seal 不无限循环 | 当前 fixture 回放全部通过；工具既有测试不回归 |
| **Batch 2：工作量削减** | P0-3 分组继承、P0-4 rename/delta、P0-6 修复与终态 | 不再全量重审，r2 只看变化和未闭环项 | 40 行覆盖不丢，unchanged 重写为 0，迁移 Diff 目标压缩 ≥80% |
| **Batch 3：基础设施与度量** | P0-7 浏览器/规划、P1 耗时与来源记录 | 降低重验税，后续有可靠 KPI | 两类真实需求 dogfood 与质量对照通过 |

不要先拆 `qa-check.mjs` 单体。先证明哪些规则应该删除或替换，再做结构重构，避免把错误状态机搬进更多文件。

## 九、验证方案与双轨 KPI

### 9.1 必测回归用例

在 `tooling/scripts/__tests__` 的既有测试体系中加入小型 fixture，不直接改写本次历史证据：

1. **Shell 闭包**：`SCRIPT_DIR + BROWSER_SCRIPT` 能发现真实 browser 断言；无候选时预检阻止派发。
2. **有限失败**：`PACKAGE_INVALID` 只返回一次明确错误；`REVIEWER_EDITABLE` 最多重试一次；429 不换模型。
3. **快照竞争**：r1 文档变更、r2 代码变更、r4 spec 变更均不能污染当前审查快照或触发修复抢跑。
4. **编号唯一**：当前 r2/r3 P-M5 冲突被识别；未 seal 原文中的 P-M6 也占据编号空间。
5. **增量继承**：未变化脚本/测试/截图被继承；内容或断言语义变化只失效相关 review units。
6. **Rename 保真**：迁移文件折叠后仍可还原前后内容，导入变化与真实行为变化不丢失。
7. **终态停止**：r2 未闭环进入 `WAITING_HUMAN`，不会自动产生 r3；人工显式授权才可追加。
8. **截图有效性**：空白、错目标和同目标取景不全走不同分支；仅图像哈希、VisualTarget 与断言语义均未变化时不重复审查，目标或断言变化必须重新核验。
9. **高风险覆盖**：权限、隐私、计费、核心链路和 changed/non-PASS 项不会因抽样被删除。
10. **来源诚实**：没有两轴有效返回与凭据时，报告只能保持待独立审查，不能写“均已 skill 派发并 seal”。

### 9.2 真实 dogfood 对照

至少两类，而不是只跑工具单测：

- **A：迁移/重命名密集型**，复用本次特性的脱敏最小 fixture，验证 Diff、继承与审查时长。
- **B：含一个真实行为缺陷的小特性**，验证测试先行修复、增量复审和 `WAITING_HUMAN`，防止系统通过少报问题提速。

建议植入本次已见过的四类变异作为质量对照：移动锚点滚错宿主、无语义绑定、空白 VisualTarget、减动效首次读取错误。它们仍被检出，才能证明降负没有变成放水。

### 9.3 质量轨（不可退让）

- 高风险行有效核验覆盖率不下降，继承行必须能追溯上一次已审哈希与原文。
- 上述变异缺陷全部检出；阶段 7 和人工终审新增语义缺陷数不得上升。
- 编号冲突、无独立返回却自称完成、无效包派发、超上限自动续跑全部归零。
- 不以“发现数下降”“required 比例下降”“一轮通过率上升”作为质量成绩。

### 9.4 效率轨（同类 fixture 对照）

| 指标 | 目标 |
| --- | --- |
| 无效审查包 | 2 秒内失败，审查子代理调用数为 0 |
| 有效包 seal | 一次通过率 100%；格式性重试最多 1 次，包错误不重试 |
| r2 重复工作 | unchanged 行重填为 0；只处理未闭环与失效 unit |
| 迁移 Diff | 目标压缩 ≥80%，且内容保真 |
| 自动轮次 | 默认 r1 + 最多一次 r2；超限进入 `WAITING_HUMAN` |
| 同类首轮审查关键路径 | 以 **≤20 分钟**为 dogfood SLO；r2 以 **≤10 分钟**为 SLO，超限记录原因而不是再开一轮 |
| 工具调用软预算 | 同类 Spec 首轮 60 次、增量 30 次触发软告警和人工决策，不直接判失败；不得再出现 164/308/125 次三轮全量排障 |
| 阶段 6 总账 | 无新增真实产品缺陷时以 **≤45 分钟**为目标；有真实缺陷时单列修复与重验，不能拿总账评价模型快慢 |

这些数值是后续 dogfood 的服务目标，不是已经实现的承诺，也不能通过删减审查内容达成。

## 十一、最终完成定义

只有同时满足以下条件，才能宣称“这次 code-review 问题已解决”：

- 相同迁移 fixture 不再出现 Spec seal 结构性失败、审查中踩脏、编号冲突和无限重试。
- r2 不再全量重读/重填，且全部高风险覆盖可追溯；rename 与增量包显著减小。
- 429、无效包和轮次上限都进入明确暂停终态，主代理不自动换模型、不直接派 Agent、不制造 r1b/r4b。
- 真实缺陷仍被检出，人工终审没有新增因降负造成的漏检。
- 两类真实 dogfood 的阶段耗时、工具调用与复审输入都有机器记录，达到或解释上述 SLO。
- 最终 `qa-check review` 的机器通过只作为门禁证据之一，仍经独立审查与人工终审，不把 PASS 当成自我授权。

**最重要的取舍**：本轮不再继续堆“更聪明的审查提示词”和“更强的表格门禁”，而是先建立四个基础事实——**审查对象不可变、证据有内容身份、发现编号稳定、复审只处理变化**。这四点成立，减少耗时和减少复审才会同时发生；缺任何一点，单纯压缩模型、轮次或 required 数量都只会把成本转移到下一次返工。
