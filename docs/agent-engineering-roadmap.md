# AI 应用工程师（Agent 方向）导师制学习与实战路线

> 「实事求是，面对现实。」—— 拒绝概念堆砌与玩具 Demo。最具有说服力的工程成果，从来不是“用了多少流行框架”，而是立足现有系统，清晰界定瓶颈，亲手定位失败，通过对照实验和量化指标证明技术动作的收益。
>
> **学习原则**：本项目的目标不是由导师交付一套系统，而是学习者亲手完成设计、编码、测试与复盘。看懂答案不等于掌握，功能跑通不等于学会。

---

## 一、 岗位定位与核心求职策略

### 1.1 目标岗位：AI 应用工程师（Agent 方向）
* **定位界定**：本路线聚焦 **AI 应用工程 / Agent 系统工程**（而非模型预训练/微调的算法岗）。
* **核心竞争力**：
  * **工程底座**：TypeScript / Python、异步任务队列、状态机持久化、并发控制、数据库与缓存、可靠性与防御性设计。
  * **Agent 专业域**：上下文与 Token 成本控制、工具有界执行与熔断重试、混合检索与重排、全链路 Tracing 与指标量化评估。
  * **面试壁垒**：能清晰讲出每一个技术动作的**前因后果、踩坑现场、对比数据与架构取舍（Trade-off）**。

## 二、导师制学习契约与使用方式

### 2.1 角色边界：学习者动手，导师引导
* **学习者负责**：回答先修自测、阅读并解释代码、作出设计决策、编写实现与测试、运行命令、记录失败、完成复盘与口头讲解。
* **AI 导师负责**：解释为什么学、讲解核心概念与取舍、带领定位代码、提出引导问题、拆分小步练习、提供分级提示、审查学习者的代码与实验结果。
* **默认不代做**：除非学习者明确要求直接实现，AI 导师不修改业务代码、不输出整文件或完整补丁、不替学习者完成阶段产物。代码评审优先指出问题与根因，由学习者修改。
* **可以使用的帮助**：阅读和搜索代码、解释报错、分析测试结果、检查学习者提供的 Diff、用最小示例说明概念。即使学习者要求完整答案，也应随后进行复述与独立复现，避免只复制不理解。

### 2.2 每次学习会话的固定闭环
1. **明确本课范围**：一次只解决一个可验证的小目标，声明本课不做什么。
2. **先修自测**：学习者先回答本阶段问题；AI 导师根据回答补基础，不默认学习者已经掌握。
3. **概念与动机**：先讲当前系统的问题、技术机制和替代方案，再决定是否写代码。
4. **代码导读**：按给定路径追踪调用链；学习者用自己的话解释关键分支，AI 导师纠正理解偏差。
5. **小步实践**：学习者独立完成一个最小改动或实验，AI 导师只提供要求、约束和必要提示。
6. **测试与诊断**：学习者先提出失败假设和排查计划，再运行测试；AI 导师帮助分析证据，而非直接给出修复。
7. **评审与 Teach-back**：学习者讲解自己的设计、测试结果和遗留风险，通过追问后记录本课结论与下一步。

### 2.3 分级提示阶梯
遇到阻碍时按顺序求助，不直接跳到答案：
1. **概念提示**：回顾相关机制，回答一个引导问题。
2. **定位提示**：指出应阅读的文件、函数、分支或日志。
3. **设计提示**：给出伪代码、状态图或测试思路，不写完整实现。
4. **最小示例**：只演示当前不懂的语法、API 或算法片段。
5. **显式代做**：学习者明确要求后才直接实现，并另外完成独立复现与讲解。

### 2.4 工程验收与学习能力验收双轨制
* **工程验收**证明系统做了什么：功能、测试、性能、质量、成本与安全指标符合要求。
* **学习验收**证明学习者能独立做什么：
  * **能解释**：不看资料讲清概念、数据流和关键取舍；
  * **能定位**：根据代码与证据找到关键路径和故障边界；
  * **能实现**：不照抄完整答案，独立完成最小闭环和测试；
  * **能诊断**：面对新故障能提出假设、设计实验并修正方案；
  * **能复盘**：说明适用范围、失败案例、替代方案和下一步改进。
* 完成功能不代表自动通过学习验收；如果只是跟做或复制实现，应安排独立复现后再进入依赖该能力的后续阶段。

### 2.5 每阶段学习档案
每个 Phase 除工程产物外，还要留下：先修自测答案、概念笔记、代码导读图、自己的设计草图、测试与失败记录、代码评审结论、三分钟 Teach-back 讲稿，以及“仍然不理解的三个问题”。这些内容优先记录真实思考过程，不追求包装成完美教程。

### Phase 0: 现有 Agent 基线盘点与 Bad Case 归因（不写新功能，先摸家底）

> **目标**：不推倒重来。基于现有的 `apps/web/src/app/api/chat/_lib/agent/agent-runner.ts` 建立客观基准，让后续每一次重构都有据可依。

#### 学习设计（先完成学习闭环，再判定阶段通过）
* **为什么学**：后续所有优化都依赖对现有编排器的准确理解。没有调用链与基线，就只能凭感觉引入框架，也无法证明优化真的有效。
* **学习目标**：能够独立追踪一次 Agent 请求，解释决策、工具、收尾与完成态落盘如何衔接；能够设计可复现基线，并把“观察到失败”与“证明根因”区分开。
* **先修自测**：
  1. 模型发起工具调用后，工具结果如何重新回到模型上下文？
  2. 为什么最大模型调用步数要包含一次收尾步？没有收尾步可能出现什么结果？
  3. 实测、估算和缺失的 Token Usage 为什么不能混为一个精确平均值？
  4. 只有 20 个样本时，P95 能说明什么、不能说明什么？
* **核心知识**：ReAct 与有界循环、SSE 数据流、工具结果回注、预算与熔断、任务成功判定、抽样与分位数、根因分析。
* **代码导读（学习者先读并讲解，导师用问题纠偏）**：
  1. `apps/web/src/app/api/chat/_lib/chat-handler.ts`：找到 Agent 分流、预算计算与 `onFinish`，说明请求入口和完成态各自负责什么。
  2. `apps/web/src/app/api/chat/_lib/agent/agent-runner.ts`：追踪主循环、工具结果回注、Usage 累加与强制收尾，画出一次两步工具调用的时序。
  3. `apps/web/src/lib/agent/tool-pipeline.ts`：定位去重、超时、连败熔断与调用上限，说明它们分别防什么风险。
  4. `apps/web/src/app/api/chat/_lib/agent/agent-config.ts` 与 `apps/web/src/lib/utils/chat-stream.ts`：核对预算常量的实际来源，并说明服务端事件如何到达客户端。
* **分步实践（学习者完成，导师只评审）**：
  1. 不看教程画出请求时序图和“内存状态 / 完成态持久化状态”清单，标出尚未理解的箭头。
  2. 先为 5 个任务编写成功判定标准，经评审后再扩展到 20~30 个，避免先跑结果再改变评分口径。
  3. 自己运行基线并保存原始结果，再计算指标；先解释异常数据，不急于优化。
  4. 选择一个真实 Bad Case，写出假设、证据、复现步骤和根因，最后进行三分钟讲解。
* **故障诊断练习**：选择一个工具超时或重复调用案例，先不看修复方案，按时间线区分首个异常、后续连锁反应与真正根因；说明还需要什么证据才能排除其他假设。
* **学习能力验收**：
  - [ ] 不看代码能画出决策步 → 工具步 → 决策步 → 收尾/落盘的完整链路。
  - [ ] 能解释预算、去重和熔断为什么分别存在，而不是只背常量。
  - [ ] 能独立设计评测任务与成功标准，并说明小样本指标的局限。
  - [ ] 能基于原始证据复盘一个 Bad Case，不把猜测写成结论。

#### 1. 现状资产与缺陷盘点矩阵
* **已具备的能力**：
  * 基于原生 TypeScript 的有界 ReAct 多步循环（默认最大 5 步）。
  * 预算控制：单步输出 Token 基准上限（2048，实际值随可负担步数与预留额度调整）、全局时间预算（240s）、工具调用次数硬顶（10 次）。
  * 容错策略：连败熔断（连续 3 次失败跳出进收尾步）、工具超时中止（派生 AbortSignal）。
  * 产物系统：Artifacts 协议与前端渲染，流式 SSE 协议与历史记录。
* **现有物理限制与缺陷**：
  * **HTTP 同步挂起**：长任务依赖同步连接，易受网关超时或客户端断网影响；240s 预算耗尽后会尝试进入收尾步，不等同于必然断连。
  * **缺少可恢复执行快照**：完成态虽有 `agent_runs` 落盘记录，但它不是 Checkpointer；执行中的任务无法凭该记录从最近节点续跑。
  * **无后台人机交互**：无法在工具执行前停下来等待用户审批，缺少 Human-in-the-loop。
  * **黑盒排障难**：中间步骤的耗时、Token 花费散落在控制台日志，无全景调用树。

#### 2. 本阶段落地动作
1. **构建初始冒烟评测集（20~30 个真实 Prompt）**：
   * 包含无工具问答、单步搜索、多步抓取合成、超时链接、参数异常诱导等场景。
   * 固定并记录模型、Prompt、工具与运行配置版本，为每个任务预先定义成功判定标准。
2. **跑出基线报告（Baseline Report）**：
   * 记录任务成功率、端到端耗时、Token 消耗与成本，并区分上游实测、缺失和估算的 Usage。
   * 20~30 个样本主要用于冒烟与失败归因，优先报告中位数、极值和原始分布；积累足够多的重复运行后再解读 P50 / P95。
3. **验证候选故障假设，沉淀真实 Bad Case**：
   * 候选假设 A：复杂检索任务触发时间预算、网关超时或客户端断连；需分别验证，不能预设因果关系。
   * 候选假设 B：模型重复调用同一失效工具，仅微调参数后持续重试。
   * 候选假设 C：网页正文膨胀挤占上下文，导致输出截断或质量下降。
   * 每个入选案例必须包含最小复现步骤、原始记录、影响范围和根因分析；未复现的假设保留为待验证项，不写成既有事实。

#### 3. 产物交付
- [ ] `docs/reports/agent-baseline-report.md`：包含评测配置版本、原始结果、失败分类，以及实际复现的 Bad Case 诊断书。

### Phase 1: AgentOps 观测度量衡建设（Langfuse + 评测体系）

> **目标**：给 Agent 装上全景 X 光机，让质量、Token、成本与耗时都可以归属和解释。

#### 学习设计（先完成学习闭环，再判定阶段通过）
* **为什么学**：没有 Trace，只能看到最终报错；没有评测，只能凭个别演示判断好坏。观测回答“内部发生了什么”，评测回答“改动是否更有效”，两者不能互相替代。
* **学习目标**：能够独立设计跨模型与工具调用的 Trace、制定脱敏和 Usage 口径，并建立可重复、可比较、包含人工校准的离线评测闭环。
* **先修自测**：
  1. Trace、Span、Generation 与普通日志有什么区别？
  2. 为什么异步任务中仅靠前端的 `traceId` 无法天然串联 Worker 调用？
  3. 上游缺失 Usage 时，成本应该如何标记和展示？
  4. 为什么 LLM-as-a-Judge 也需要人工校准？
* **核心知识**：分布式追踪与上下文传播、结构化事件、指标与成本归因、数据脱敏和采样、评测有效性、裁判偏差、回归对比。
* **代码导读**：
  1. `apps/web/src/app/api/chat/_lib/agent/agent-runner.ts`：找出每次模型调用与工具执行的自然 Span 边界，以及 Usage 缺失时的现有处理。
  2. `apps/web/src/app/api/chat/_lib/chat-handler.ts`：追踪完成回调、结算和 `agent_runs` 落盘，思考哪些标识必须在入口创建并向下传递。
  3. `apps/web/src/lib/agent/tool-pipeline.ts` 与 `packages/logger/src/index.ts`：比较结构化业务事件和普通日志，确定哪些字段值得观测、哪些必须脱敏。
  4. `packages/db/src/ai-usage.ts` 与 `packages/db/src/billing/usage-measurement.ts`：理解 Usage 归一化、估算与计量的现有语义，避免另造一套冲突口径。
* **分步实践**：
  1. 先在纸上设计 Trace 树、标识传递和字段脱敏表，说明每个 Span 的开始、结束与异常语义，经评审后再选择 Langfuse 接入方式。
  2. 独立打通“一个模型调用 + 一个工具调用”的最小观测闭环，验证异常路径后再扩展，不一开始全量埋点。
  3. 基于 Phase 0 数据集实现自己的最小 Eval Runner，先输出带版本信息的原始结果，再增加聚合指标与基线对比。
  4. 对一批样本进行人工评分，与 LLM 裁判结果比较并分析分歧；用户反馈 UI 最后再做。
* **故障诊断练习**：构造或模拟一次 Usage 缺失、一次工具异常和一次含敏感参数的工具调用，检查 Trace 是否仍能串联、错误是否可见、凭证是否泄漏，以及估算值有没有被伪装成实测值。
* **学习能力验收**：
  - [ ] 能解释 Trace、日志和指标各自回答的问题，并独立为一个新工具设计 Span。
  - [ ] 能说明标识在 Web、队列与 Worker 之间如何传播，而不是只在单点生成。
  - [ ] 能复现同口径评测，并解释模型、Prompt、数据集或配置变化对比较结果的影响。
  - [ ] 能分析一项人机评分分歧和一项脱敏风险，提出可验证的改进。

#### 1. 核心任务与改造点
1. **集成 Langfuse 分布式 Tracing**：
   * 在请求入口启动 Root Trace，携带 `traceId`、`runId`、`conversationId`、`sessionId`；用户标识按需匿名化，避免上报不必要的个人信息。
   * 模型推理封装为 `Generation`：按策略上报脱敏后的输入 Prompt 与补全内容、Model ID，以及 Token Usage 的数据来源（`actual` / `estimated` / `missing`）；成本记录模型价格版本，不与实测 Usage 混为一谈。
   * 工具调用封装为 `Span`：按策略上报脱敏后的 Tool Name、入参、出参、执行耗时、错误、超时与缓存命中情况。
   * 制定采集与保留策略：默认剔除凭证和敏感字段，必要时采样或仅记录元数据，并限制看板访问权限。
2. **自动化评测运行器（Eval Runner）**：
   * 编写基于现有评测集的离线自动化测试脚本：`pnpm test:eval`。
   * 建立分层测试用例集（冒烟集、工具正确性集、异常鲁棒性集），记录数据集、模型、Prompt 与配置版本。
   * 评测任务成功率、工具选择与参数正确率、异常收敛率、延迟和成本；引入 LLM-as-a-Judge 时，使用人工抽样校准并保留分歧案例。
3. **用户显式反馈回路打标（不阻塞离线评测闭环）**：
   * 改造前端卡片：增加「点赞 / 点踩 / 报错反馈」按钮。
   * 反馈通过轻量接口实时上报为 Langfuse `Score`，与对应的 `traceId` 强绑定；显式反馈作为质量信号之一，不替代标注评测集。

#### 2. 产物交付与量化结果
- [ ] 每个被评测的 Agent 会话均可在 Langfuse 看板上查到完整调用树瀑布流（Waterfall），且日志不含明文凭证。
- [ ] 产出系统基线仪表盘：样本量充分时展示 P50/P95 耗时、单次会话成本（USD/次或美分/次）、工具调用错误率与任务成功率。
- [ ] `pnpm test:eval` 输出带版本信息的质量、延迟与成本报告，可与 Phase 0 基线进行同口径对比。

### Phase 2: 可靠的长任务单 Agent 架构重构（异步化 + 状态机 + HITL）

> **目标**：解决同步长连接与执行状态不可恢复的问题，打造支持长耗时、高容错、可恢复的深度研究 Agent。

#### 学习设计（先完成学习闭环，再判定阶段通过）
* **为什么学**：长任务的核心难点不是调用 LangGraph API，而是分布式执行中的状态归属、重复投递、崩溃恢复和外部副作用。只学会框架语法，仍然可能做出会重复扣费或重复写入的系统。
* **学习目标**：能够独立设计可恢复状态机，解释至少一次投递与幂等的关系，实现断线恢复和 HITL，并基于真实约束决定是否使用 LangGraph。
* **先修自测**：
  1. 为什么消息队列的“至少一次投递”意味着消费者必须考虑重复执行？
  2. 外部工具已经成功、本地尚未写入 `tool_done` 时崩溃，为什么不能直接重试？
  3. Checkpointer、完成态历史记录和 Redis PubSub 分别解决什么问题？
  4. 页面刷新后，SSE 已错过的事件应该从哪里恢复？
* **核心知识**：状态机与状态迁移、队列投递语义、快照与版本、幂等键和唯一约束、不确定故障窗口、并发恢复、事件补拉、HITL。
* **代码导读**：
  1. `apps/web/src/app/api/chat/_lib/agent/agent-runner.ts` 与 `apps/web/src/app/api/chat/_lib/chat-handler.ts`：列出当前仅存在于请求内存中的状态，以及完成态才落盘的数据。
  2. `apps/worker/src/index.ts` 与一个现有 Worker（如 `apps/worker/src/workers/ppt.ts`）：追踪任务从入队到消费、成功和失败的路径。
  3. `packages/queue/src/queues.ts` 与 `packages/queue/src/jobs.ts`：理解项目现有队列和 Job 契约，标出重试、超时与重复投递需要验证的位置。
  4. `packages/db/prisma/schema.prisma` 与 `apps/web/src/lib/utils/chat-stream.ts`：比较持久化记录和实时流事件，设计重连后各自应承担的角色。
* **分步实践**：
  1. 先画 Planner、Searcher、Reflector、Writer 与 `waiting_approval` 的状态图，再为每个迁移标注持久化时机、副作用和崩溃窗口；未通过评审前不写框架代码。
  2. 不依赖 LangGraph，用普通 TypeScript 实现一个最小状态机恢复练习，验证“保存快照 → 模拟崩溃 → 读取快照 → 继续执行”，理解机制后再做架构选型。
  3. 先独立打通一个简单长任务的异步纵向切片：创建任务、Worker 消费、持久化进度、刷新后恢复展示；通过后再接入 Agent 循环。
  4. 自己增加 HITL、幂等恢复与故障注入测试，记录每次预测和实际结果；最后撰写 ADR，说明继续自研或采用 LangGraph 的依据。
* **故障诊断练习**：在测试环境模拟“外部副作用成功后未提交”和“重复 Resume”，运行前先预测系统会发生什么，运行后用数据库记录、工具调用次数和事件序列验证；若出现重复副作用，先定位不确定窗口再谈修复。
* **学习能力验收**：
  - [ ] 能从零画出状态图，解释每个状态的进入条件、持久化点和合法迁移。
  - [ ] 能实现不依赖框架的最小恢复练习，并说明它与生产级 Checkpointer 的差距。
  - [ ] 能讲清为什么状态标记不等于幂等，以及不同副作用分别如何防重。
  - [ ] 能设计断线补数、重复投递和旧版本快照测试，并解释 LangGraph 选型取舍。

#### 1. 架构选型与深入思考（面试必考点）
* **思考题**：*“继续基于现有 `agent-runner.ts` 增强，还是迁移到 LangGraph？”*
  * **手写增强方案**：在现有代码上引入显式状态机与序列化快照。优点是轻量、无外部框架开销、完全可控；缺点是复杂的条件分支拓扑与人机中断需要手写大量状态迁移样板代码。
  * **LangGraph 方案**：专为循环图设计，提供 Checkpointer 规范与 `interrupt` 语义；缺点是有一定学习成本、包体积与迁移成本。Checkpointer 不等于自动完成业务 State Schema 迁移，旧快照兼容策略仍需自行设计。
  * **决策路径**：先用 ADR 记录两种方案针对当前任务的权衡，再决定是否迁移。无论使用 LangGraph 还是自研状态机，核心都是**状态可持久化（Snapshot）与恢复执行（Resume）**，而非框架名称。

#### 2. 落地设计：Deep Research 深度研究智能体
1. **Web 与 Worker 职责解耦**：
   * Web 端发起请求 → 入库生成任务记录并推入 BullMQ 队列 → 立刻返回 `taskId`，由 `apps/worker` 消费。
   * Worker 负责驱动长耗时状态机步进，持久化节点状态与当前输出，同时通过 Redis PubSub 广播实时状态与 Token 增量；前端通过 SSE `/api/agent/stream?taskId=xxx` 订阅渲染。
   * PubSub 只承担实时通知，不作为历史事件仓库。页面刷新或断网重连后，先拉取持久化快照恢复展示；若要求事件级连续回放，则为事件持久化单调递增序号，并通过 `Last-Event-ID` 或 `afterSeq` 补拉断线期间的事件。
2. **状态拓扑与检查点（Checkpointer）**：
   * 定义结构化状态：目标规划、已收集笔记、反思意见、当前步骤计数、当前输出与 Artifact 引用。
   * 每一个节点（Planner / Searcher / Reflector / Writer）执行完毕后自动落盘。任务记录与可恢复快照优先以 Postgres 为持久化事实来源，Redis 用于队列、实时通知与可重建缓存。
   * 状态中显式携带 `stateVersion`，定义旧版本快照的迁移或废弃策略；恢复时校验任务状态与版本，防止重复 Resume 请求并发推进同一任务。
3. **人在回路（Human-in-the-Loop, HITL）**：
   * Planner 节点生成调研大纲后，触发中断（Interrupt），任务进入 `waiting_approval` 挂起状态。
   * 前端渲染交互卡片，用户可增删研究子课题。
   * 用户点击确认后，Resume API 校验任务归属与挂起状态，再以幂等方式触发 Worker 从挂起点继续执行。
4. **副作用幂等与故障注入验证（硬核亮点）**：
   * 为每次工具调用生成跨重试稳定的幂等键（如 `runId + nodeId + toolCallId`），记录 `tool_pending` / `tool_done` 与可核验的执行回执；状态标记本身不等于副作用去重。
   * 只读工具可安全重试；数据库写入使用唯一约束、事务或幂等记录防重；外部服务优先消费上游 Idempotency Key，不支持时提供结果查询、对账或补偿机制。
   * 重点覆盖“外部已成功、本地尚未写入 `tool_done` 时 Worker 崩溃”的不确定窗口：恢复后不能仅凭 `tool_pending` 盲目重放；无法确认结果且不可逆的操作转入人工确认。
   * 故障注入覆盖工具执行前、外部副作用成功后未提交、Checkpoint 写入后、重复投递与 Worker 重启等场景，并核验外部副作用实际次数。

#### 3. 产物交付与量化结果
- [ ] 支持 15 分钟以上的后台异步深度长任务，页面刷新或断网重连后能凭持久化快照恢复当前状态与输出；若承诺事件连续回放，须通过补拉测试。
- [ ] 产出故障注入用例、样本量、原始记录与恢复成功率报告，并验证外部副作用不会因恢复而重复发生。

### Phase 3: Advanced RAG 知识检索管道构建（高召回与低幻觉）

> **目标**：不搞花架子，针对专业知识问答，搭建一套可测量的多路召回、重排与可核验引用管道，同时评估答案质量、延迟与成本。

#### 学习设计（先完成学习闭环，再判定阶段通过）
* **为什么学**：RAG 的核心不是把文档塞进向量数据库，而是控制解析、召回、排序、上下文和引用每个环节的信息损失。没有标注集与对照实验，就无法知道混合检索或 Rerank 是否真正解决问题。
* **学习目标**：能够独立实现并评估最小检索管道，手算核心指标，解释各组件的适用边界，并处理引用、权限和不可信文档带来的风险。
* **先修自测**：
  1. 为什么专有编号和错误码可能需要词法检索，而不能只依赖稠密向量？
  2. PostgreSQL `ts_rank` 与 BM25 是不是同一个算法？
  3. 给定两路文档排名，如何手算 RRF？为什么它不依赖原始分数量纲？
  4. 为什么 Rerank 无法找回粗排阶段没有召回的文档？Hit Rate@3 提升为什么不等于幻觉下降？
* **核心知识**：文档解析与切块、Embedding、词法与稠密召回、中文分词、RRF、Cross-Encoder、Hit@K 与 MRR、Faithfulness、引用校验、ACL 与间接提示注入。
* **代码导读**：
  1. `apps/worker/src/index.ts` 与一个现有离线 Worker：理解文档解析和索引任务可以怎样复用现有队列，而不是塞进同步请求。
  2. `packages/db/prisma/schema.prisma`：梳理现有用户、会话和任务数据边界，再设计文档、切片、版本与 ACL 数据模型。
  3. `packages/storage/src/index.ts` 与 `packages/storage/src/local-provider.ts`：理解原始文件和派生产物的存储边界，思考删除文档时还需要清理什么。
  4. `apps/web/src/lib/agent/registry.ts` 与 `apps/web/src/app/api/chat/_lib/agent/runtime-context.ts`：研究如何把检索作为受权限约束的工具接入现有 Agent，而不是绕开工具治理。
* **分步实践**：
  1. 先手工处理一份小文档：切块、写出 5 个查询及相关切片，手算 Hit@3、MRR 和一组 RRF 结果，经导师核对后再写代码。
  2. 独立实现一个针对小型排名列表的 RRF 函数及测试，不借助现成库；随后建立单向量基线并保存逐题结果。
  3. 自己增加词法召回与混合检索，比较失败案例变化；只有数据证明有净收益时才加入 Rerank，不用组件数量衡量完成度。
  4. 最后补充稳定引用、无答案拒答、ACL 和恶意文档测试，并解释每个测试防的是什么风险。
* **故障诊断练习**：选取一个“错误码明明存在却召不回”的案例，依次检查解析、切块、分词、召回和重排，不得一开始就更换 Embedding 模型；再用一个跨用户文档请求验证权限过滤发生在检索之前。
* **学习能力验收**：
  - [x] 能手算 RRF、Hit@3 和 MRR，并解释指标背后的用户价值。（实现见 `apps/web/src/eval/rag/metrics.ts`，手算对拍单测见 `apps/web/src/eval/rag/metrics.test.ts`）
  - [x] 能独立搭建最小检索对照实验，根据逐题结果而不是总体感觉做结论。（真机运行器见 `tooling/scripts/eval-rag.mts`，32 题逐题对照见报告第四节）
  - [x] 能说明 Rerank、长上下文和父文档策略各自的局限与代价。（深度归因详见 `docs/reports/rag-eval-report.md` 第三节）
  - [x] 能设计可核验引用、拒答、权限隔离与提示注入测试，并区分检索质量和答案质量。（自动化流水线见 `apps/web/src/eval/rag/rag-pipeline.eval.test.ts`，32 组标准题集见 `apps/web/src/eval/datasets/rag-smoke.jsonl`）

#### 1. 核心任务与技术细节
1. **文档解析与感知语义的切块策略**：
   * 扩展 Worker 解析器：先支持文本型 PDF / Markdown / DOCX，明确扫描 PDF、OCR 与复杂表格是否属于当前阶段范围。
   * 避免机械字数切块：采用分层递归切块（基于 Markdown 标题或自然段落），按需保留父子文档层级（Parent-Document Retriever），并记录 `documentId`、`documentVersion`、`chunkId` 与页码或字符偏移等定位信息。
   * 为文档更新、删除与重建索引定义一致性行为，避免旧版本切片继续被召回。
2. **多路召回融合（Hybrid Search via RRF）**：
   * **向量检索路**：pgvector 稠密向量检索，捕捉语义相似度。
   * **词法检索路**：PostgreSQL 可使用 `tsvector` + `ts_rank` / `ts_rank_cd` 作为全文检索基线，但不得将其称为 BM25；需要 BM25 时使用 SQLite FTS5 `bm25()`、支持该算法的 PostgreSQL 扩展或搜索组件。
   * **中文查询分析**：明确中文分词、英文大小写、编号与错误码的处理策略，避免算法正确但因分词不当导致漏召回。
   * **RRF 排名融合**：
     $$RRF\_Score(d) = \sum_{m \in M} \frac{1}{k + r_m(d)} \quad (k=60)$$
     合并两路排序候选（初始可取 Top-20），作为无需跨路分数校准的稳健基线；是否优于归一化加权等方案由同口径实验判断。
3. **Cross-Encoder 二次重排（Rerank）**：
   * 接入 BGE-Reranker 模型，对粗排候选重新打分，并根据评测选择进入模型的 Top-N；只有质量收益足以抵消新增延迟与成本时才保留该阶段。
4. **防御性设计：降低注入风险与可核验引用溯源**：
   * **间接提示注入防护**：以来源标签将检索内容标记为不可信数据，但明确标签不是安全边界。工具权限最小化、参数校验、网络策略与高危操作人工确认必须在模型之外实施；使用恶意文档验证其无法诱导危险工具调用或数据外发。
   * **引用溯源**：要求模型输出 `[^1]` 等引用，并用程序校验引用是否存在、是否支持对应结论。默认提供段落或页码级定位；只有解析器保留可靠行坐标时才承诺行级定位。前端通过稳定文档版本与锚点高亮原文，而非依赖易变化的显示行号。
5. **多租户权限与数据边界**：
   * 在检索阶段即按用户、知识库与文档 ACL 过滤，而不是生成答案后再过滤；权限变更、文档删除与缓存失效需要一致性测试。
6. **RAG 离线量化评测实验**：
   * 先建立 30 组标注冒烟集（问题、参考答案、相关文档或切片），覆盖可回答、不可回答、跨段落与恶意注入样本；得出稳定结论前扩充样本并进行必要的重复运行。
   * 对比实验：【单纯向量检索】vs【混合检索】vs【混合检索 + Rerank】，固定语料、模型与评测口径，记录 Hit Rate@3、MRR、延迟与成本。
   * 增加端到端答案评测：答案正确性、Faithfulness、引用正确率与覆盖率，以及无答案问题的拒答表现；检索指标提升不能直接等同于低幻觉。

#### 2. 产物交付与量化结果
- [x] 完整的知识库上传、解析、检索调试面板，以及文档版本、权限隔离和删除更新的一致性测试。（工单 01~10 全部落地打通）
- [x] 评测报告包含样本量、原始结果、检索指标、答案与引用指标、延迟和成本；仅根据实测结果说明 RRF 或 Rerank 是否带来净收益。实测报告详见：[`docs/reports/rag-eval-report.md`](reports/rag-eval-report.md)（四组对照矩阵完备：验证 RRF 稳健融合；证实百切片规模下 Rerank 边际增益极微且延迟暴增 120%，客观决策默认关闭）。

### Phase 4（选修）: 标准 MCP 工具接入 或 安全代码沙箱（二选一做深）

> **决策建议**：不要两个都做半吊子。如果目标团队偏向生态集成与平台化，选 **4A**；如果偏向数据分析、研发助手与高安全执行，选 **4B**。

#### Option 4A: 标准 MCP（Model Context Protocol）协议客户端
##### 学习设计
* **为什么学**：MCP 的价值是标准化工具发现与调用，不是增加一个流行依赖。只有先理解现有工具注册、权限和模型 Schema 映射，才能判断哪些胶水代码值得被协议替代。
* **学习目标**：能够解释 MCP 生命周期与传输边界，独立接入一个只读 Server，并处理 Schema、命名、超时、鉴权和服务故障。
* **先修自测**：MCP 与 Function Calling、Webhook 分别解决什么问题？Capabilities 协商发生在什么阶段？为什么允许普通用户任意配置 Stdio Server 可能等同于执行任意命令？
* **核心知识**：JSON-RPC、握手与 Capabilities、Tools/Resources、Schema 映射、传输、鉴权、工具命名空间与最小权限。
* **代码导读**：
  1. `apps/web/src/lib/agent/registry.ts` 与 `apps/web/src/app/api/chat/_lib/agent/runtime-context.ts`：解释现有工具如何注册、过滤并投影给模型。
  2. `apps/web/src/app/api/chat/_lib/agent/tools/user-webhook.ts` 与 `apps/web/src/schemas/agent-tool.schema.ts`：梳理私有工具的参数校验、鉴权和执行边界，找出 MCP 可以统一与不能替代的部分。
* **分步实践**：先画现有 Tool 调用时序和 MCP 握手时序；再由学习者接入一个只读 Server，独立完成 Schema 映射和最小测试，通过后再增加第二个 Server 与治理能力。
* **故障诊断练习**：模拟工具重名、非法参数、服务超时和未授权挂载，先预测系统应在哪一层拒绝，再用测试验证不会误调工具或无界等待。
* **学习能力验收**：能脱离 SDK 文档讲清一次 MCP 调用链；能独立映射一个新 Tool Schema；能说明协议标准化之后仍需自行解决的权限与故障问题。
* **核心内容**：
  * 基于 `@modelcontextprotocol/sdk` 封装客户端，统一工具发现、描述与调用；必要时保留私有 Webhook 适配器，两者并非天然替代关系。
  * 完成握手与 Capabilities 协商、Tool Schema 映射和参数校验，处理工具命名冲突、超时与服务不可用。
  * 在管理员配置与允许列表下接入 Filesystem 和只读 Postgres MCP Server；普通用户不能任意启动本地 Stdio 进程或挂载未授权远程服务。
* **面试亮点**：讲透专有 Function Calling 胶水代码与标准化协议的区别，以及协议标准化不能替代鉴权和权限治理。

#### Option 4B: 安全隔离的 Python 代码解释器沙箱
##### 学习设计
* **为什么学**：代码解释器让 Agent 能处理真实数据，也把模型输出变成了潜在不可信程序。启动容器只是工程开始，真正的学习重点是威胁模型、隔离边界和资源治理。
* **学习目标**：能够根据部署环境选择隔离方案，独立实现受限制的最小执行器，并用无副作用的安全测试验证边界。
* **先修自测**：Pyodide 与服务端 Docker 的信任边界有何不同？为什么断网不能阻止所有越权？除 CPU 和内存外，为什么还需要限制进程数与输出大小？
* **核心知识**：威胁建模、WebAssembly 与容器隔离、非特权执行、只读文件系统、资源限额、网络策略、产物提取与安全测试。
* **代码导读**：
  1. `apps/worker/src/index.ts`：分析执行器放在哪种 Worker 边界中最容易隔离资源和故障。
  2. `packages/storage/src/index.ts` 与 `apps/web/src/app/chat/chat-workspace.tsx`：追踪产物存储和展示位置，设计沙箱输出如何成为受限 Artifact。
  3. `apps/web/src/lib/agent/tool-pipeline.ts`：确定超时、错误和工具结果治理应怎样覆盖代码执行工具。
* **分步实践**：先写资产、攻击者、入口和信任边界清单；比较 Pyodide 与容器并写选型 ADR；再由学习者实现只能运行无害计算的最小执行器，逐步加入资源限制、CSV 分析和图表产物。
* **故障诊断练习**：用受控的无限循环、超限输出和网络 Canary 验证超时、输出限制与网络隔离；运行前写明预期，不执行真实破坏性命令。
* **学习能力验收**：能画出沙箱信任边界并解释每个控制点防什么；能独立验证一项资源限制；能说明“测试没有逃出沙箱”与“证明沙箱绝对安全”之间的区别。
* **核心内容**：
  * 先定义威胁模型、部署位置与不可信输入边界，再选择浏览器 Pyodide、独立 Worker 中的 WebAssembly 或服务端容器池；不将 Pyodide 或 Docker 单独等同于完整安全边界。
  * 强边界防御：默认禁止出站网络、只读文件系统、非特权用户、无宿主机凭证与 Docker Socket 挂载，并限制内存、CPU 时间、进程数与输出大小。
  * 验证用例：使用无副作用的探测文件与网络 Canary 验证越权读取、网络访问和资源限制，不执行真实破坏性命令。
  * 业务结合：上传 CSV 数据表格，Agent 编写 Python 进行聚合统计并渲染交互图表。

### Phase 5（验证与深化）: Multi-Agent 架构对照实验

> **警惕陷阱**：多智能体很容易沦为“为了用而用”的负优化（Token 增多、延迟上升、排障复杂）。本阶段的目标是**用数据判断 Multi-Agent 在哪些任务上有净收益，负结果同样是有效结论**。

#### 学习设计（先完成学习闭环，再判定阶段通过）
* **为什么学**：多智能体最值得学习的不是角色扮演，而是架构假设如何通过实验被证实或证伪。能够得出“单 Agent 更合适”的结论，比搭建一个昂贵但无收益的专家团队更重要。
* **学习目标**：能够提出可证伪的架构假设，设计控制变量与重复实验，分析质量、延迟和成本，并解释结论的适用边界。
* **先修自测**：为什么单个成功案例不能证明多智能体更好？如果两组使用不同模型和工具，结果会混入哪些变量？为什么增加角色不必然缩短总耗时？
* **核心知识**：Supervisor 与专家路由、上下文隔离与交接、协作预算、实验假设、控制变量、重复测量、盲评与结论外推边界。
* **代码导读**：重新阅读 `apps/web/src/app/api/chat/_lib/agent/agent-runner.ts` 与 `apps/web/src/lib/agent/registry.ts`，明确 Single Agent 基线；复用 Phase 1 的 Eval Runner 和 Phase 2 的状态持久化产物，避免为实验另建一套不可比口径。
* **分步实践**：先写假设、任务集、成功标准和控制变量，由导师评审实验设计；学习者再分别实现最小 Single 与 Multi-Agent 版本，重复运行并保留逐次结果；最后先写分析结论，再决定是否值得进入生产架构。
* **故障诊断练习**：构造两个子 Agent 反复交接或关键上下文丢失的案例，利用 Trace 找出通信轮次、信息损失和额外成本分别发生在哪里。
* **学习能力验收**：能设计没有明显混淆变量的对照实验；能解释结果波动与样本限制；能接受负结果；能明确列出不应该使用 Multi-Agent 的场景。

#### 1. 对照实验设计
* **任务选取**：建立一组包含简单任务与复合任务的评测集，而不是只用单个复合任务下结论；预先定义成功标准并保留原始输出。
* **控制变量与重复运行**：两组使用相同模型、输入数据、等价工具能力与最大预算，分别充分调优并记录配置；每个任务重复运行多次，报告样本量、分布与波动，避免用单次运行证明优劣。
* **对照组（Single Agent）**：使用挂载全部所需工具的单个 Agent。
* **实验组（Multi-Agent）**：Supervisor 负责拆解工单，派发给专精的 Researcher、Coder、Reporter 子智能体，各子智能体保持精简私有上下文。
* **度量维度**：
  * 任务最终达成度（人工盲评/金标对比）；
  * 端到端耗时及其分布；
  * 总消耗 Token 与成本（USD）；
  * 按明确判定标准记录的工具失败、无依据陈述与死循环频次。
* **面试表达模板（实测后填写，不预设结论）**：
  * *“在 N 个任务、每任务 R 次重复运行中，Single 与 Multi-Agent 的质量、延迟和成本分别为……；只有在……任务分组中观察到……，因此最终选择……。这些结论的适用范围和样本限制是……。”*

## 四、面试深水区考点与实操防御库

**使用方法**：学习者先不看“防御话术”独立回答，AI 导师再连续追问“为什么、还有什么方案、失败时怎么办”。回答卡顿时回到对应代码或实验补证据，不背诵标准答案。

| 考点方向 | 面试官经典追问 | 实事求是的防御话术与底层原理 |
| :--- | :--- | :--- |
| **编排器选型** | *“为什么用 LangGraph 而不继续用原生循环手写？”* | 不是因为原生写不出来，现有版本就是原生实现的。如果最终选择 LangGraph，核心权衡应是：长任务异步化后，状态恢复、条件分支和并发控制全手写的维护成本较高，而 LangGraph 规范了 Checkpointer 接口和中断机制。同时也要说明迁移成本，以及业务 State Schema 的版本迁移仍需自行设计。 |
| **混合检索打分** | *“向量分数和 BM25 分数为什么不能直接相加？RRF 是唯一方案吗？”* | 两路原始分数量纲和分布不同，直接相加缺乏可比性；但经过合理校准或归一化后仍可加权融合，也可以学习排序。RRF 只使用各路的**相对排名（Rank）**，是无需跨路分数校准的稳健基线，并非在所有数据集上都最好，应与加权方案做同口径对照。 |
| **Rerank 的真实局限** | *“加了 Reranker 就彻底解决检索准确度了吗？它有什么副作用？”* | Reranker 只是对粗排候选重新打分：① Cross-Encoder 逐对计算通常会增加延迟与成本；② **无法弥补召回盲区**，前置召回没捞到的候选无法靠重排恢复；③ 检索指标提升也不必然带来最终答案质量提升，因此需要端到端评测。 |
| **长任务容错** | *“Worker 在外部工具成功后、状态提交前崩溃，怎么避免重复副作用？”* | 仅靠 `tool_pending` / `tool_done` 无法消除这个不确定窗口。需要跨重试稳定的幂等键，并由数据库唯一约束、上游 Idempotency Key 或可查询回执真正消费；无法确认执行结果时通过对账、补偿或人工确认处理，不能仅凭 `tool_pending` 自动重放。 |
| **断线恢复** | *“Redis PubSub 广播 Token，用户刷新后如何补齐断线期间的内容？”* | PubSub 只负责实时通知，任务状态与当前输出必须持久化。重连后至少拉取最新快照；若要求事件级连续回放，则保存带单调序号的事件，并用 `Last-Event-ID` 或 `afterSeq` 补拉。 |
| **提示注入防御** | *“网页抓取工具抓回来的内容里包含恶意指令诱导 Agent 删库，怎么防？”* | 不能只靠系统提示词或 XML 标签。来源标签只是辅助模型区分数据与指令，真正的安全边界在模型之外：① 检索内容按不可信输入处理；② 工具最小权限、严格参数校验与网络隔离；③ 高危操作必须经 Human-in-the-loop 确认；④ 用恶意样例核验危险调用和数据外发确实没有发生。 |
| **RAG 评测** | *“Hit Rate@3 提升，是否就能证明系统幻觉降低？”* | 不能。Hit Rate 与 MRR 只评价检索，还需评价答案正确性、Faithfulness、引用正确率与覆盖率，并加入无答案样本检验拒答。只有端到端指标也改善，才能谨慎说明答案可靠性提升。 |

## 五、简历项目描述黄金模板（工程化表达）

在简历中彻底抛弃“负责编写某某功能”的流水账，采用 **【痛点问题 → 架构动作 → 测量收益 → 取舍思考】** 结构。以下 `N` / `R` / `X` / `Y` 均为占位符；未实现、未实测或无法提供原始记录的内容不得写入正式简历，样本量与评测口径必须能够接受追问。简历内容必须来自学习者亲手完成并能现场讲解的模块，而不是导师代做的成果。

### 项目经历：全栈 AI 聚合平台与 Agent 系统重构

* **基于状态机与异步队列重构长任务执行架构**：
  * 针对原同步长连接易中断且缺少可恢复执行快照的问题，将执行层解耦至 **BullMQ Worker**，并使用 **Postgres** 持久化任务状态与当前输出；
  * 基于状态图拓扑设计规划、执行与反思回路，实现节点粒度 Checkpointer 与 **Human-in-the-Loop** 审批；通过持久化快照或事件补拉支持断线恢复；
  * 针对外部副作用设计幂等键、唯一约束与结果核验机制，覆盖“外部成功、本地未提交”故障窗口；在 N 类故障、R 次注入测试中，恢复成功率为 X%，外部副作用重复次数为 Y。

* **构建可量化评测的 Advanced RAG 知识检索管道**：
  * 针对专业文档专有名词与编号检索漏召回的问题，搭建融合 **pgvector 与词法全文检索** 的混合检索系统（具体词法算法按实际实现填写），利用 **RRF** 融合多路召回排名；
  * 引入 **BGE-Reranker** 对候选片段进行二次交叉精排，并基于稳定文档版本与锚点建立段落或页码级引用溯源；
  * 在 N 组标注样本上，相比单向量基线，混合检索 + Rerank 的 Hit Rate@3 由 X% 变为 Y%，同时报告答案正确性、引用指标、延迟与成本，说明质量收益是否足以抵消额外开销。

* **搭建 AgentOps 全链路分布式 Tracing 与度量体系**：
  * 集成 **Langfuse**，针对 Agent 多步循环、模型推理与工具调用建立 Waterfall 链路追踪，实现分阶段耗时与成本归因；区分实测、估算和缺失的 Token Usage，并落实敏感数据脱敏；
  * 搭建用户显式反馈与带版本信息的离线评测基准，在 N 个任务、R 次运行中跟踪任务成功率、延迟和成本，形成 Bad Case 驱动的持续调优闭环。

## 六、结业能力验收与启动方式

### 6.1 结业不是勾完所有任务
* 主线 Phase 0~3 必须通过学习能力验收；Phase 4A / 4B 按目标岗位选择至少一项做深；Phase 5 只在有明确假设和实验价值时进行。
* 学习者需要完成一个此前没见过的小型需求，从澄清、代码定位、设计、实现到测试独立走通；AI 导师只能使用分级提示，不能提供完整实现。
* 学习者需要完成一次现场故障诊断、一次可复现对照实验和一次架构 Teach-back，能够主动说明系统的局限与下一步，而不是只展示成功路径。
* 最终求职材料应能由学习档案中的代码、测试、原始实验和复盘互相印证；无法回答追问的内容不写入简历。

### 6.2 第一课启动方式
学习者直接提出：**“开始 Phase 0 第一课：读懂一次 Agent 多步工具调用。”** AI 导师按以下顺序带学，不直接修改代码：
1. 学习者先回答 Phase 0 的四个先修自测题，暴露需要补齐的概念。
2. AI 导师讲解 ReAct、决策步、工具步、收尾步和 Usage 累加，并说明为什么这些知识与后续长任务架构有关。
3. 双方按 `chat-handler.ts` → `agent-runner.ts` → `tool-pipeline.ts` 的顺序读代码；学习者先解释，导师再纠偏。
4. 学习者独立画出一次工具调用的时序图和状态清单，提交给导师评审。
5. 通过代码导读验收后，再进入评测集设计与真实基线实验。

> **下一步行动**：从 **Phase 0 第一课** 开始，不预先阅读完整答案，不要求导师直接实现。先表达自己的理解，再用代码和实验证据修正它。
