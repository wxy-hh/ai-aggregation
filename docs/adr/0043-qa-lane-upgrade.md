# 0043. QA 车道升级

* **状态**：已接受
* **日期**：2026-10-31
* **范围**：QA 工作流正本与指南、implement / to-spec / to-tickets / qa-test-planner 技能与安装模板
* **相关**：ADR-0024（阶段收口与唯一后继）

## 背景

正本规定车道在阶段 1 裁决，后续技能沿用，不重新判定。这条规则随三车道路线引入，用意是让每个技能收口只给本车道路线的下一个命令，但没有处理阶段 1 判错的情况。按快车道开工后才发现改动跨多模块时，现有规则只覆盖「快车道触及核心链路补精简 qa-plan 与阶段 5」，没有升级出口，判错的大改动可能不经双轴审查就交付。

决策经 /grill-with-docs 逐题拷问，每题由 GPT-5.6 Sol 与 Kimi K3.1 Pro 独立核对后收敛。

## 决策

1. **触发与确认**：实现中的事实不再符合当前车道在判定表中的标准时，Agent 停下，报告依据与建议车道；用户确认后补齐新车道缺少的阶段。只升不降，Agent 不提议降级。触发条件沿用现有判定表，不另立标准。
2. **补齐路线**：沿用当前特性目录。快车道升标准车道时，由用户手动运行 `/grill-with-docs`（只追问未决事项）、`/to-spec`、`/qa-test-planner`；标准车道升慢车道时必须补 `/to-tickets`，即使最终仍串行实现。
3. **旧证据与基线**：升级前的 qa-run 日志保留作历史，不作为本轮证据；init 前执行记录不得有 PASS 行。基线标签用 `baseline-upgrade-*`，范围说明写明「含在途改动，非原始开工前基线」；基线红灯先问用户，不得记为既有失败。
4. **在途改动**：未提交的改动在 init 后立即对同一批路径执行 `add`。已提交的改动在范围说明记下起始提交，把 `<起点>..HEAD` 的 diff 作为补充材料交双轴审查；起点不明确时停下请用户指定。升级前已实现的工单保持 `ready-for-agent`，正文注明「升级前已实现，待新基线复验」。
5. **落点**：`/implement` 增加触发条款；`/implement-spec` 不加，慢车道已是最高车道。to-spec、to-tickets、qa-test-planner 的收口改为沿用当前车道。CLAUDE.md 不改。

## 考虑过的选项

- **Agent 自行升级、只在汇报中说明**：补 spec 需要调用只能由用户触发的技能，Agent 自行补写违反「不伪造调用」。
- **维持现状，交付时说明判错**：判错的大改动可能不经双轴审查就交付。
- **快车道升级时跳过 grill**：`/to-spec` 依赖 grill 已确认的接缝，快车道从未确认过；grill 只问未决事项时成本很低。
- **已提交改动改写历史后重建基线**：reset、rebase 须二次确认，为补审查改写历史不划算。代价是补充 diff 的完整性只能由人工终审核对。

## 后果

- 车道判错有了合法出口，代价是多一次中断，「是否仍算小修」依赖 Agent 判断，可能报早或报晚。
- 已提交在途改动的审查完整性无法由检查器核对。
- 本决策只描述机制，不宣称质量或耗时收益；效果以下一次真实需求的 dogfood 为证据。
- 停止条件沿用 ADR-0031/0033/0035。
