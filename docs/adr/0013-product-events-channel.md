# 0013. 自建最小产品事件通道 `product_events`（不用第三方分析 SDK）

* **状态**：已接受
* **日期**：2026-10-10
* **决策者**：AI 聚合平台工程团队
* **范围**：`packages/db`（新表迁移）、`apps/web`（`POST /api/events`、前端 `trackEvent` 封装）

---

## 背景

ROADMAP 横切事项要求「埋点统一进现有观测通道」，但事实是**通道不存在**：项目无任何前端行为埋点体系（无 posthog/umami/gtag/sentry），服务端仅有计费用量（`ai_usage_records`）与 webhook 工具审计（`webhook_tool_calls`）两条业务侧数据线。

P0a 子项 2 的智能升级芯片是第一个强依赖：ADR-0012 明确「二期 L2 分类器由芯片曝光/点击数据决定」，没有埋点等于芯片上线即盲飞、词表迭代无依据。后续 ROADMAP 项（能力包点击、工具启停、确认通过率、任务复跑率）全部假设此通道。

## 决策

**自建最小事件通道**，三件套：

1. **新表 `product_events`**：`id, userId, event, props Json, createdAt` + `(userId)`、`(event, createdAt)` 索引；
2. **`POST /api/events`**：`requireAuth` 鉴权 + 节流（对齐现有 API 限流档）；body 校验 event 名白名单（防前端乱写污染）；
3. **前端 `trackEvent` 封装**：fire-and-forget（不阻塞交互、失败静默），芯片曝光/点击/dismiss 为首个消费者。

**隐私红线（随表一并生效）**：`props` 只放事件元数据（如 `{ signal: 'url'|'keyword', keyword?: '<词表条目>', action: 'impression'|'click'|'dismiss' }`）；**URL 原文、消息内容、对话片段绝不入事件**。词表是前端公开常量，记录命中哪个词属最小必要。

**范围控制**：本期只做「通道 + 芯片事件」，不做事件后台/可视化报表——分析直接跑 SQL；报表需求是 P0b 之后的事。

## 备选方案及否决理由

1. **接入第三方分析（posthog/umami 等）**：*否决理由*：用户行为数据出域（含 userId 关联），与产品自有计费/会话数据 join 分析需额外 ETL；且本项目事件量级（内部工具向）远未到需要专业分析平台的程度，自建一张表 SQL 足够。
2. **挂服务端文本日志（前端打点到 log）**：*否决理由*：无结构化查询能力，「点击率 = 点击数/曝光数」这种基础问题都要靠 grep 聚合，等于半残；日志还会随轮转丢失。
3. **复用 `webhook_tool_calls` 或 `ai_usage_records` 硬塞**：*否决理由*：那是工具执行审计与计费用量两条业务线，语义各自单一；混入产品行为事件会破坏既有查询口径。
4. **本期不埋、二期再建**：*否决理由*：ADR-0012 的 L2 决策路径整个落空。

## 后果

- 正面：ROADMAP 全部后续埋点项（能力包/工具启停/确认通过率/复跑率）有统一落点；隐私口径在建表时锁死；与 `webhook_tool_calls`（工具执行线）形成「用户行为 × 工具执行」互补双通道。
- 负面/权衡：自建意味着分析靠手写 SQL（无漏斗/留存现成功能）；event 名白名单需要随新埋点项维护（接受——白名单本身就是防污染机制）。
