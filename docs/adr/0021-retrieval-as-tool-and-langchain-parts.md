# 0021. 检索能力以只读工具形态接入自研 ReAct 循环与 LangChain 零件库定位架构

* **状态**：已接受
* **日期**：2026-10-23
* **决策者**：AI 聚合平台工程团队
* **范围**：`apps/web`（Agent 编排、工具注册表、运行时上下文、RAG 检索管道）、`packages/shared`（场景能力包）、`packages/db`

---

## 背景

在为 AI 聚合平台的 Agent 体系建设知识检索增强（RAG）能力时，团队面临两项核心架构决策：
1. **检索流程的接入模式**：是将检索作为硬编码的前置拦截路由（Pre-retrieval），还是以工具形态（Retrieval-as-a-Tool）接入模型有界自研 ReAct 循环？
2. **三方框架的依赖边界**：是否引入 LangChain.js / LlamaIndex 作为端到端 RAG 与 Agent 编排框架？

在业界常见实现中：
- **前置硬编码路由**：在请求到达模型前，强行用轻量分类器或规则判定是否查库，把召回切片直接塞入 System Prompt。该模式剥夺了模型的灵活性，无法支持多轮细化搜索、跨工具协同（如先查内部知识库、缺失时再联网补充）以及双源路由（知识库文档 vs 会话记忆）；对于无需查库的对话，强塞切片还会造成严重的上下文污染与 Token 浪费。
- **全量引入 LangChain / LlamaIndex 编排层**：虽然开箱即用，但其 Chain、AgentExecutor、VectorStore 等多层抽象充斥大量隐式副作用，错误栈深不可测，重试与流式取消难以精细控制，且无法复用平台已打磨成熟的配额原子结算、连败熔断、出图硬上限等关键治理机制。

---

## 决策

### 1. 检索能力全面建模为标准只读工具接入自研 ReAct 循环

我们将私有知识库检索统一封装为 **`knowledge_search`** 只读工具，直接接入现有成熟的工具执行管道：
- **模型自主选源（双源路由）**：在普通 Agent 循环中，由模型根据用户意图自主决策何时调用 `knowledge_search` 查文档、何时调用 `memory_search` 查历史对话记忆、何时直接作答，实现真正的动态语义路由。
- **装配层动态过滤（无库用户零负担，QA-010）**：在运行时上下文（`createAgentRuntimeContext`）装配层，若当前用户名下无任何有效知识库，自动从挂载工具集中剔除 `knowledge_search`。无库用户完全不感知检索工具，杜绝无意义的 Prompt Token 浪费。
- **双保险安全多租户隔离**：工具执行强制从请求上下文获取 `ctx.userId`，底层 SQL 实行 ACL 前置硬过滤；即使模型被诱导传入他人的 `knowledgeBaseId`，在工具内部立即校验并拦截，严防跨租户越权。
- **【不可信检索内容】包裹与注入防御 (QA-012)**：检索结果统一使用安全标签包裹，明确标注为只读事实数据，并注入严格指令要求模型忽略切片文本中可能包含的恶意系统指令，安全边界锚定在工具入参校验与沙箱之外。

### 2. 双入口架构设计：通用自适应 + 专精场景能力包

为了兼顾通用场景的自适应便捷性与专业问答的高确定性，提供“双入口”：
- **入口一：通用 Agent 自适应入口**：默认开启 Agent 即可用，模型根据问题复杂度自适应决定单步或多步检索，与联网搜索、绘图工具无缝混排。
- **入口二：`knowledge-qa` 专精场景能力包（ADR-0014 演进）**：
  - 白名单收敛：严格限定为 `['knowledge_search', 'web_search', 'web_fetch']`，物理隔离出图等非问答工具；
  - 步数上限：设定为 5 步探索预算；
  - 专属系统提示词：明确要求以知识库内容为第一信源，强制在关键事实后使用 `[^n]` 标注引用出处，且知识库无匹配内容时坚决明确拒答（QA-011），杜绝幻觉编造。

### 3. 程序化引用核验与锚点跳转 (QA-004)

- 每一条返回的检索切片均附带结构化物理锚点 `CitationAnchor`（文档名、单调递增版本号、页码或标题层级）。
- 新增 `citation.ts` 模块，程序化核验正文中的 `[^n]` 编号是否真实映射到召回切片，识别并记录越界幻觉编号。
- 前端消息气泡支持将 `[^n]` 渲染为可点击交互的徽标元素（`CitationBadge`），点击可展开气泡查看出处并支持跳转定位原文。

### 4. LangChain.js 的零件库定位

- **严禁引入** LangChain 的 Chain、AgentExecutor、VectorStore、Memory 等运行时编排类；
- **允许且仅允许** 将 LangChain 作为纯无状态低层算法的零件库使用（如 `@langchain/textsplitters` 的分块切词算法），输入输出为纯粹的数据结构，零外部 I/O 与运行时状态，保持平台基础设施的完全自主可控。

---

## 后果

### 正面收益
1. **架构极简与单一事实源**：检索工具与其他内置工具（`web_search`、`image_generate`）完全对齐相同的生命周期、超时策略、连败熔断与审计链路，零架构裂化。
2. **多源自适应路由**：模型能够根据上下文在同一会话中无缝串联知识库检索与外部事实检索（如先搜内部文档规范，再搜外部对应版本的 API），表达力远超前置规则管道。
3. **安全与隔离确定性**：无库用户自动剔除工具，有库用户强制租户 ACL，恶意内容标记为不可信上下文，各层防御清晰可测。
4. **轻量可维护**：避免了 LangChain 框架升级带来的破坏性变更，核心 ReAct 逻辑始终保持百行规模的透明性与确定性。

### 负面影响与应对
- **模型遵从度要求**：依赖模型对工具调用指令与引用标记 `[^n]` 的依从能力。平台已基于 `deepseek-flash` 模型进行了严格测试，并在系统提示词与检索内容包裹区设计了强化防幻觉提示，实测引用忠实度与拒答率均达标。
