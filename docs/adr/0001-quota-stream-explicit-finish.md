# 0001. 配额流式结算管道深化（onFinish 显式终态声明）

* **状态**：已接受
* **日期**：2026-09-23
* **决策者**：AI 聚合平台工程团队
* **范围**：`apps/web/src/app/api/destiny` 域流式路由配额结算协议

---

## 背景

在 `destiny` 域下，多条 Server-Sent Events (SSE) 路由（如星语问答 `copilot`、星座报告 `astrology/report`、八字合盘 `compatibility-report`）此前共用 `report-generation.ts` 中的浅管道 `withQuotaStream` 来托管流生命周期并结算配额。在实际生产与集成测试中，该浅层管道暴露出三个结构性缺陷：

1. **业务失败误判为部分计费（误扣费风险）**：
   路由的业务异常处理逻辑通常会在 `catch` 块中将上游模型调用失败转换为流内的 SSE `error` 事件并推送给客户端，随后正常关闭流（`controller.close()`）。`withQuotaStream` 仅依据底层流是否正常结束以及管道中是否有累计产出文本（`hasOutput`）进行推断，误将这种情况判定为 `partial`（部分成功扣费）。结果导致用户在前端界面仅看到错误卡片，但底层配额却被扣除。
2. **成功终态依赖隐式标记（易漏调与标签错位）**：
   `success` 终态严重依赖业务层是否记得手动调用 `reporter.markCompleted()`。一旦业务方漏调或在异常分支之后误触发，管道就会将完成的流判定为截断或错误，破坏了配额对账的标签可信度。
3. **推迟预留带来的类型与状态垫片**：
   部分流式场景（如星盘真值先于模型推理下发）在流启动并推送真值后才触发 `QuotaSession.reserve`，为了在构建流管道时传入未就绪的会话，旧管道引入了 `{ current: QuotaSession | null }` 的 holder 垫片，带来了不必要的联合类型复杂度和悬挂风险。

---

## 决策

彻底废弃原有的隐式猜测管道 `withQuotaStream`，在 `apps/web/src/app/api/destiny/_lib/quota-stream.ts` 中引入以 **显式终态声明**（`control.finish`）为核心的新管道，将配额终态判定的决定权完全交还业务方，管道本身严格退化为“恰好结算一次”的安全守卫。

锁定的 6 条核心结算语义如下：

1. **业务方显式声明终态（优先且幂等）**：
   业务方通过 `control.finish({ outcome, usage?, outputText?, reason? })` 主动声明结算结果（`success` / `partial` / `failed`）。该声明具备幂等性，仅首次调用生效，后续调用静默忽略。声明时若尚未绑定会话，属编程错误：记录 `console.error` 并跳过结算（与决策 3 的"未绑定静默跳过"不同——那是流关闭而业务从未声明的合法无预留路径）。
2. **连接取消（Cancel）兜底**：
   当客户端主动中断连接（`ReadableStream.cancel`）且业务方尚未声明终态时，管道执行兜底推断：`hasOutput ? 'partial' : 'failed'`（这是整个架构中唯一允许管道凭现场产出推断的分支）。
3. **未声明正常关闭 Fail-Closed（安全熔断）**：
   当底层流正常关闭（`done: true`）但业务方未声明终态时：
   - **已绑定会话**：触发 **Fail-Closed** 机制，强制按 `failed` 结算（整额释放预留），并打印 `console.error` 告警，确保编程遗漏在第一时间暴露，绝不让用户承担平台未定义行为的成本；
   - **未绑定会话**：静默跳过（兼容额度不足提前退出等合法未预留路径）。
4. **底层读取异常兜底**：
   当 `reader.read()` 抛出异常且未显式声明终态时：
   - **已绑定会话**：按现场文本判定 `hasOutput ? 'partial' : 'failed'`，`reason` 记录错误信息；
   - **未绑定会话**：静默跳过。
5. **业务侧终态声明原则**：
   - 用户仅看到错误卡（仅接收到 `error` 事件，无有效业务产出）：必须声明 `failed`，由平台承担上游成本；
   - 用户已拿到部分有效内容（如报告中部分核心分区已渲染）：声明 `partial`。
   
   **错误卡收尾即失败的细化口径（2026-09-23 评审裁定）**：星语问答（copilot）与八字合盘（compatibility-report）中，凡以错误卡收尾的流——即便报错前已有部分正文增量流出——一律声明 `failed`。理由：问答类产出上限小（2048 输出 token），半截回答以错误卡收尾的用户体验就是"失败"，"失败不收钱"的承诺价值大于这几分钱的成本；且合盘路由从不向客户端下发中间正文，错误卡即零产出。`partial` 仅保留给两类场景：报告路由已送达的完整分区（按 `sectionsSent` 计量），以及 cancel/读异常兜底中用户已拿走的正文。
6. **结算异常安全**：
   管道内部所有 `session.finalize` 调用均由 `try/catch` 保护，结算失败仅输出错误日志（后续由系统用量对账兜底），严禁向业务流中抛出异常中断响应。

## 备选方案及否决理由

1. **方案 A：修补 `withQuotaStream` 的黑盒推断规则**：
   * *思路*：在管道内部通过解析 SSE 事件内容（如检测数据流中是否含有 `event: error`）来猜测业务是否失败。
   * *否决理由*：严重违反关注点分离原则。管道不应侵入业务事件格式的编解码与逆向解析；且不同业务流的错误事件 schema 各不相同，黑盒解析不可维护、极其脆弱。
2. **方案 B：chat 域式 `onFinish` 参数直传流工厂**：
   * *思路*：仿照 chat 域适配器协议，把 `onFinish` 回调作为参数传入 `generate(ctx, body, onFinish)` 流工厂。
   * *否决理由*：`astrology/report` 的会话必须晚绑定（星盘真值帧先于额度预留下发），chat 域"会话先于流存在"的前提不成立，onFinish 直传仍需要额外的可变容器来晚绑定会话；同时需要改动 `createReportHandler` 的适配器协议签名。control 对象方案（`bindSession` + `finish`）实质是它的严格超集。
3. **方案 C：管道内部收编 `QuotaSession.reserve`**：
   * *思路*：由 `createQuotaStream` 内部代为执行预留逻辑。
   * *否决理由*：各路由的预留时机各异。例如星座报告需要先经 150ms 本地运算输出 `chart-facts` 之后才预留，而问答路由则在请求校验通过后立即预留。将预留时机与参数强行绑死在管道内会破坏业务流程的编排自由度。

---

## 后果

### 正面收益
1. **终态判定权归位**：业务层完全掌控用户的实际交付体验，消除了“用户看错误卡却被扣费”的顽疾，平台扣费与释放界限清晰可信。
2. **架构消除垫片**：彻底移除了 `billingHolder` 与 `{ current: null }` 等临时补丁，`control.bindSession` 明确区分了未预留与已预留阶段。
3. **对账标签确定性**：成功必有 `usage`，截断与失败必有 `reason` 与精确 `outcome`，大幅提升了计费日志与财务对账的准确性。
4. **防御性 Fail-Closed**：流意外退出或业务漏声明会即时通过控制台告警并安全释放，杜绝了悬挂会话与隐蔽扣费。

### 潜在代价与应对
* **业务方开发责任增加**：业务路由在新增流分支时必须明确在成功点与 catch 点调用 `control.finish`。
* **应对措施**：未声明会自动触发 `fail-closed` 告警并在单测与开发阶段暴露，配合完善的测试用例守卫防止遗漏。
