# 0014. 场景能力包与会话级工具子集装配机制

* **编号**：ADR-0014
* **状态**：已接受
* **日期**：2026-10-11
* **决策者**：AI 聚合平台工程团队
* **范围**：`apps/web`（`chat-workspace`、`chat-store`、`conversations-store`、`runtime-context`、`agent-runner`、`agent-config`）、`packages/db`

---

## 背景

在 ROADMAP P0b 阶段，解决平台「供给与反馈闭环」的核心问题。用户在面对通用 Agent 时缺乏明确的交付预期（不知道它能做什么），且在会话中无法感知或按需控制模型持有的工具（例如本次会话不想让模型调用生图工具）。

在设计「场景能力包（CapabilityPack）」与「Chat 内可用工具面板（SessionToolOverride）」时，面临以下架构与产品取舍：
1. **工具供给组织形式**：零散的单点工具插件 vs 预置固定专业流水线；
2. **能力包与自定义工具关系**：白名单严格绝对闭包 vs 开放用户 Webhook 扩展插槽；
3. **工具启停的作用域与存储**：纯内存 vs 会话级持久化 vs 全局设置；
4. **工具调用回流机制**：全量工具写库 vs 复用并轻量扩展现有 `WebhookToolCall` 表。

## 决策

1. **首发 2 个垂直打磨的场景能力包**：
   - `deep-research`（深度调研）：强制限定内置工具为 `['web_search', 'web_fetch']`，步数上限上调至 8 步（提升递归检索深度与交叉验证能力），注入学术/专业结构化研报系统提示词；
   - `visual-report`（图文报告）：限定内置工具为 `['image_generate', 'web_search']`，维持 5 步上限，注入图文构思与排版输出系统提示词；
   - 未指定能力包时为 `general`（通用模式），全量开放已启用的内置工具。
2. **基线收敛 + 扩展插槽模型**：
   - 场景能力包对**平台内置工具**实施强制白名单约束，防止跨领域能力串味（如调研包禁止生图）；
   - 对**用户自定义 Webhook 工具**作为个性化扩展插槽开放，允许用户在会话内按需启用（例如调研产出后转发至个人飞书/钉钉群机器人）。
3. **会话级工具覆盖（Session-Scoped Overrides）**：
   - 能力包绑定与工具启停状态随 `Conversation` 实体持久化至客户端 `localStorage`，页面刷新或历史会话切换时无缝还原；
   - 新建会话重置为初始状态，杜绝跨会话状态污染。
4. **请求差异契约与服务端双重安全闸门**：
   - 前端向 `/api/chat` 请求时携带 `capabilityPack?: string` 与 `disabledToolKeys?: string[]`（差异减项传参）；
   - 服务端第一道闸门严格依据服务端能力包配置过滤内置工具（防客户端篡改白名单），第二道闸门仅按当前用户校验启用的 Webhook 并应用禁用项。
5. **观测回流轻量复用已有审计实体**：
   - 工具调用回流聚焦解决用户 Webhook 工具缺乏反馈的问题，直接复用既有 `WebhookToolCall` 表及关联关系，避免内置高频抓取产生冗余数据库负载。

## 备选方案及否决理由

1. **单点工具散卖/单独打成能力包（如天气包、汇率包）**：*否决理由*：陷入零件思维，无法给用户提供完整的交付物体验；简单工具通过 Webhook 即可自建。
2. **能力包严格绝对闭包（禁止任何 Webhook）**：*否决理由*：切断了用户在专业工作流中衔接私有工具（通知、CRM、知识库）的可能性，降低了可扩展性。
3. **通用的全量 `tool_call_logs` 统一大表**：*否决理由*：当前阶段内置工具（多次 web_fetch 抓取）行数爆炸且缺乏业务消费场景；用户真正关切的是自己配置的 Webhook 是否存活。

## 后果

- **正面**：
  - 用户从空态页可一键进入明确预期的垂直场景，体验大幅提升；
  - 会话级状态隔离清晰，刷新不丢且互不干扰；
  - 架构保持轻量，数据库零阻碍平滑演进。
- **负面 / 注意事项**：
  - 调研包步数上限调至 8 步，在配额结算时 `resolveAgentStepBudget` 的预留计算必须适配 `maxSteps`，防止高并发场景下步数超支或误判额度不足。
