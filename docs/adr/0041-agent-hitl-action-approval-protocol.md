# 0041. 受控写操作与人机协同审批协议 (AGENT-HITL-ACTION)

* **状态**：已接受
* **日期**：2026-10-30
* **决策者**：AI 聚合平台工程团队
* **范围**：`packages/db`（`UserWebhookTool` 新增审批字段及迁移）、`packages/shared`（`chat-stream-contract` 的 `tool_approval_request` 事件、审批卡片数据模型）、`apps/web`（`tool-pipeline` 审批拦截、`user-webhook` 适配器、`chat-handler` 恢复请求入口与验签、审批凭证模块、`agent-tools` 工具设置表单与 API、`ApprovalCard` 组件与消息持久化）
* **关联计划**：`docs/plans/chat-agent-evolution-plan.md`（Phase 3 P2：`AGENT-HITL-ACTION`）
* **关联决策**：ADR-0008（工具执行管道）、ADR-0038（计划卡片与流中断恢复先例）、ADR-0039（步数预算）

---

## 背景

现有 Agent 工具中，唯一能产生外部副作用的是用户自定义 Webhook 工具（`method` 为 `GET | POST`，默认 `POST`）。它们在模型决定调用后由 `tool-pipeline` 立即出站，用户无法在执行前确认。计划文档的红线要求「任何涉及用户数据覆写或外部系统变更的操作，严格走人在回路（HITL）确认」，验收指标为「误触发与高危写操作事故率为 0」。

计划文档中的 `send_email`、`update_record` 目前并不存在，本期不新增内置写工具。

## 决策

### 1. 作用范围：只管用户 Webhook 工具

- 本期不新增任何内置写工具；审批协议挂在 Webhook 工具适配器与工具执行管道上，将来内置写工具可复用同一协议；
- 复用现有 SSRF 防御、凭证加密与 `ToolCallAudit` 审计，不另建出站通道；
- 会话级工具停用先于审批生效；能力包白名单现状只收敛内置工具、不过滤用户 Webhook 工具，本期不改变，审批对任何能力包下的 Webhook 写工具同样生效。

### 2. 写操作分级：显式字段

- `UserWebhookTool` 新增布尔字段（暂名 `requiresApproval`）。新建时 `POST` 默认 `true`、`GET` 默认 `false`，用户可在工具设置中修改；
- 存量记录迁移时，`POST` 工具一律置为 `true`，`GET` 工具置为 `false`，安全优先；
- 选择显式字段而非按 HTTP 方法推断：「POST 做只读查询」很常见，按方法推断会让用户无法关掉确认；「GET 带副作用」会绕过确认。
- 代价：需要一次 DB 迁移（生产部署多一个步骤），并修改 schema、表单与 API。存量 POST 工具的行为会变化（原来直接执行，之后需确认）。

### 3. 暂停与恢复：流结束 + 新请求恢复

- 模型调用需审批工具时，服务端推送 `tool_approval_request` 事件后**正常结束本次流**，不挂起连接、不保留服务端会话状态。与 ADR-0038 的「中止后携带上下文发起后续请求」思路一致；
- 用户确认后，前端发起新聊天请求，携带原对话历史、计划已完成检查点与审批凭证；
- 服务端验签通过后**直接执行被批准的那一次调用**，把「调用 + 结果」合成一对工具消息注入上下文，模型据此继续 ReAct 循环。模型不重新决策，参数不可能被改动；
- 恢复请求不再触发 Planner，沿用已有计划，不重复下发 `plan_created`；
- 暂停前那一轮已执行的只读工具结果不带到恢复请求，模型需要时会重新查询，占用新请求的步数与工具次数预算。恢复请求按一次新的聊天请求结算额度，预算重新计算。
- 代价：同一任务可能重复检索，多耗一点额度；暂停前的推理过程不保留。
- 未采用方案：挂起长连接（受 240 秒预算约束，页面离开即作废，多实例需共享路由状态）；服务端快照完整运行状态（需存储大体积工具结果，与 ADR-0022 的隐私边界冲突，工作量超出本期）。

### 4. 审批凭证：HMAC 签名 + Redis 一次性

- 凭证绑定用户 ID、会话 ID、工具 ID、参数（哈希）与过期时间，有效期 10 分钟，用服务端密钥做 HMAC 签名；
- 验签通过后以 Redis `SET NX`（TTL 等于有效期）标记已用，重放即拒绝；
- **Redis 不可用时失败关闭**：拒绝执行写操作并提示稍后重试。代价是 Redis 抖动期间写操作暂时不可用；
- 需要新增一个签名密钥环境变量，生产部署需补配；
- 未采用「仅签名 + 有效期，不防重放」：用户双击确认或网络重试会让写操作执行两次，与「误触发事故率为 0」冲突。

### 5. 同轮多调用：遇首个写操作即暂停

- 单轮最多 3 个工具调用（`AGENT_MAX_TOOL_CALLS_PER_ROUND`）。按顺序执行，遇到第一个需审批调用就推送审批请求并结束流，**其后的同轮调用全部不执行**；
- 排在它前面的只读调用已执行，结果不带入恢复请求；
- 一次只审批一个调用，凭证只绑定一个调用。
- 代价：恢复后模型要重新决策被丢弃的调用，多一次模型往返。

### 6. 卡片动作：确认 / 拒绝，不做参数编辑

- 卡片展示工具名、目标域名与参数，只有「确认执行」与「拒绝」；
- **偏离计划文档**：计划文档写的「修改参数」本期不做。参数编辑表单需按 Webhook 参数定义动态渲染并校验，移动端复杂度高，凭证还需绑定改后参数并二次 schema 校验。想改参数时，用户拒绝后用自然语言让模型重新发起；
- 拒绝是**纯前端终止**：卡片置为「已拒绝」并落盘，不发请求、不调用模型、不耗额度。下一轮对话的历史里带一句「用户拒绝了执行 X」，模型可见；
- 代价：拒绝后模型不会自动给出替代方案，用户需再开口；改一个字段要多一轮对话。

### 7. 卡片落盘与失效

- 审批请求作为消息的一等字段随消息落盘（沿用 ADR-0038 的 `plan` 字段做法），状态为待确认 / 已确认 / 已拒绝 / 已失效；
- 刷新后，10 分钟有效期内的待确认卡片仍可点击；超时或其后已有新消息则自动变「已失效」，用户需重新提需求。前端判断仅用于展示，**最终以服务端校验为准**；
- 卡片不污染正文 Markdown，导出保持干净。

### 8. 审计

- 推送审批请求时写一条 `ToolCallAudit`，`outcome = pending_approval`（`outcome` 为字符串字段，无需改表，需同步更新 schema 注释）；用户确认执行后按现有逻辑再写 `success` / `failed`；
- 拒绝是纯前端动作，服务端不记录；「有 pending 无后续执行」即可推断被拒绝或已过期；
- 工具成功率等统计须把 `pending_approval` 排除在分母之外；
- 暂停不计入 `AGENT_MAX_WEBHOOK_CALLS` 的实际派发次数；恢复执行的那一次计入新请求的计数。

### 9. SSE 契约

在 `packages/shared/src/chat-stream-contract.ts` 新增 `tool_approval_request` 事件，携带调用 ID、工具名、目标域名、参数、审批凭证与过期时间。未知事件类型客户端已显式忽略，旧客户端不受影响。

---

## 代价与权衡

- **体验**：写操作一律多一次点击与一次恢复请求的等待；拒绝后需用户再开口；
- **成本**：恢复请求多一次模型调用，且暂停前的只读检索可能重复；
- **运维**：新增签名密钥环境变量与 DB 迁移；写操作依赖 Redis 可用；
- **兼容**：存量 POST 工具行为改变，需在发布说明与工具设置页给出提示。

## 效果证据说明

「误触发与高危写操作事故率为 0」是机制性保证：执行路径只接受被批准那一次调用的有效凭证，且凭证一次性。本决策不声称对任务成功率或用户满意度有收益；如需此类结论，须另行设计可复现的对照评测。

## 本决策不覆盖（留给 spec）

- 审批字段的最终命名、迁移脚本与工具设置页文案；
- 签名密钥环境变量名与密钥轮换策略；
- 恢复请求的请求体字段与服务端校验顺序；
- 审批卡片在窄屏下的布局（需符合 `DESIGN.md` 与移动端红线：热区 ≥ 44×44，底部安全区）。
