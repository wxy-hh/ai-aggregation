# 0017. 通用内置联网搜索 (WebSearch) 与高韧性网页精读 (WebFetch) 协同架构

* **状态**：已接受
* **日期**：2026-10-14
* **决策者**：AI 聚合平台工程团队
* **范围**：`apps/web`（`agent-runner`、`tools/web-fetch`、`tools/web-search`、`tools/index`）

---

## 背景

在 Agent 工具体系中，用户反馈联网任务频繁失败、Token 浪费严重、回答残缺无重点。
现场证据与根因分析表明存在四大系统性缺陷：
1. **搜索能力供给缺位**：此前 `web_search` 仅作为火山方舟 Ark 专属工具挂载在豆包模型下；用户选择 DeepSeek 等主流模型时无搜索工具，导致模型自作聪明地用 `web_fetch` 爬取 Bing/DuckDuckGo 的 HTML 搜索结果，引入极高延迟与噪音，频繁触发单请求 10 次工具调用熔断上限；
2. **网页抓取 200KB 硬上限粗暴熔断**：`web-fetch.ts` 规定体积超过 200KB 即直接 `res.destroy()` 并抛出 `ToolError`。现代云平台开发文档、定价页（如智谱 `docs.bigmodel.cn`、MiniMax `platform.minimaxi.com`）HTML 体积普遍在 300KB~1.5MB，导致核心事实页面 100% 抓取失败；
3. **爬虫 User-Agent 暴露遭防爬拦截**：使用显式 Bot 标识，遭云厂商 CDN/WAF 拦截返回登录跳转或无客户端水合的 SPA 空壳（正文仅 14 字）；
4. **缺乏搜索与精读的两步收敛范式**：模型在无明确指导下陷入“搜索→失败→换词再搜→抓大页面报错”的死循环。

---

## 决策

1. **构建平台通用内置 `web_search` 检索工具**：
   - 作为独立内置工具注册至默认工具库，**对 DeepSeek、豆包、讯飞等全模型无差别开放**；
   - 采用双轨自适应架构：若配置了专业商业检索 Key（如 `TAVILY_API_KEY`）走商业接口；默认无 Key 环境自动平滑走内置的免密清洗检索流，输出结构化线索 `{ title, url, snippet }`（前 3~5 条）；
   - 从根源上消除非豆包模型对爬虫拼 URL 搜 Bing 的依赖。

2. **重构 `web_fetch`：放宽安全上限至 2MB + 平滑截断提取（永不抛错）**：
   - 接收缓冲区上限由 `200KB` 提升至 `2MB`，覆盖绝大多数重型文档与官方站；
   - 流式接收达到 2MB 时，**立即优雅截断停止接收，对已接收到的前 2MB 数据正常清洗并提取正文**，不抛出致命异常；
   - 提取出的正文严格受到 `MAX_CONTENT_CHARS = 8000` 约束，末尾附带截断说明，保障模型能读到网页关键前半部分（标题、概要、前置定价表格）。

3. **现代桌面浏览器请求头伪装与极简空壳识别提示**：
   - 替换 Bot UA 为主流桌面 Chrome 浏览器真实请求头，绕过静态 WAF 针对爬虫的误杀；
   - 当抓取到的纯文本极短（<50 字符）且命中典型单页应用/拦截特征时，友好返回提示：“该页面主要依赖客户端 JS 动态渲染或需登录，请参考已有搜索线索继续推理，避免重复尝试该地址”。

4. **规范提示词：两步收敛检索范式**：
   - 在 Agent System Prompt 中明令禁止使用 `web_fetch` 抓取搜索引擎页面；
   - 引导模型遵循：`web_search 关键词定位外链 → 挑选 1~2 个最权威 URL 用 web_fetch 精读 → 立即组织最终专业回答` 的高效两步闭环，将总调次稳定收敛在 2~3 次以内。

---

## 后果

- **正面**：
  - DeepSeek 等模型获得真正原生的联网检索能力，回答完整度与时效性大幅提升；
  - 智谱、MiniMax 等大型官方文档站可 100% 成功读取有效正文，告别“内容过大已放弃”；
  - 调次从原先打满 10 次熔断急剧下降至 2~3 次，Token 消耗减少 60%~75%，端到端响应时间缩短 5~10 秒。
- **负面 / 注意事项**：
  - 纯无头免密检索源受公共网络波动影响，生产环境建议配置商业检索 Key（如 Tavily）获得确定性 SLA。
