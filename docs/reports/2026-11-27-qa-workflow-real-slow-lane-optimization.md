## 1. 最终结论

这次运行不能记为成功交付：最终停在 `WAITING_HUMAN`，S-H3、P-M5、P-M7 未闭环，`pnpm test` 仍有 5 个既有外部依赖失败，r3 来源仍只能按弱凭据和人工核对处理。独立双轴找到了真实缺陷，复审上限也阻止了自动修复死循环，这些防线必须保留。

从第一性原理看，目标不是继续增强门禁，而是最小化：

> **真实缺陷漏出的预期成本 + Agent 验证成本 + 用户决策与等待成本 + 流程自身维护成本。**

最终建议不立 `v2.3`、不改 Schema 4、不新增凭据身份协议，按以下顺序独立交付：

1. **先修确定性工具缺陷**：编号解析、混合 changed 骨架、`seal` 状态覆写、`qa-run` 错误可观测性。
2. **用只读摘要拦截旧审查包**：不在 collect 中无条件重跑 acceptance；同时明确 `WAITING_HUMAN` 的物理停手白名单。
3. **用少量规则消除高成本行为**：基线范围隔离、读盘认领、禁止并发重派已封存轴、测试假绿定级、需求与播报减法。
4. **单独验证 `reviewUnits` 继承失效**：这是高潜在收益项，但必须通过变更盲测后才能放宽；不能靠忽略证据哈希换取继承率。

`qa-run` 交付批执行降为低优；删除手填 PASS 表放在继承修复之后做消融；不采用 TC 标题硬锁、哈希自动升强、跨 app 强引生产内部构造器或合并多题拷问。

## 3. 成本排序后的根因

### 3.1 P0：四个确定性工具缺陷持续制造无效工作

1. **finding 解析漏掉 Standards**：当前只认方括号编号，r1 的 17 条 Standards 未进入登记器和骨架；但 `## 实际核对范围（无发现部分）` 又触发宽泛的无发现正则。
2. **Spec 骨架与 seal 自相矛盾**：骨架把 changed 与 unchanged 断言合并，预填同一个变更复核值；校验器却要求 unchanged 必须为「不适用」。r1/r2/r3 Spec 均为 `sealAttempts: 2`，转录可见首次失败正是这一冲突，见 `.scratch/eval-real-execution-honest-scoping/_qa/spec-review-skeleton.md:8-10`、`tooling/scripts/qa-spec-review.mjs:106-140`、`:392-399`。
3. **失败 seal 覆写已封存轴**：`sealReview` 在检查 `.source.json` 是否存在之前先写 `challenge.axes` / `manifest.axes`，见 `tooling/scripts/review-package.mjs:465-479`；`recordSealFailure` 还会把已 `returned` 的轴改为 `failed`，见同文件 `:390-410`。
4. **`startedAt` 不是审查开始时间**：它在首次 seal 时才生成，r1 Standards 出现毫秒级 started/completed，r3 Spec 的长审查被误读为约 2 分钟。该字段不能再用于计算审查耗时。

此外，`qa-run` 的重名错误没有统一可过滤前缀，直接诱发了本次旧日志误当新日志的问题。

### 3.2 P0：审查包新鲜度与跨会话物理隔离不足

旧 acceptance、旧绑定和旧清单能进入审查包；两个主会话又能对同 nonce 重派并覆盖同一组文件。仅告诉 Agent“不要重派”不够，工具必须先检查已存在凭据，主流程必须以 `.source.json` 为已封存真源。

### 3.3 P1：`reviewUnits` 的证据哈希让真实增量继承失效

`spec-coverage.mjs:179-195` 把日志文件名和内容哈希编入 `evidenceHash`，而执行记录又在任一实现变化后整体改指新测试日志，导致未改测试和断言的单元也无法继承。r1→r2 实测有 7 个此类单元。

但 r2→r3 清单本身没有重新生成，所以不能进一步推断所有轮次都只有同一个根因。放宽继承前，必须先解决清单新鲜度，再验证“哪些依赖变化真的会使旧结论失效”。

### 3.4 P1：测试假绿与规则执行偏差造成重复修错

- 自造生产不存在的 `checkpoint_updated`；
- 空完成夹具漏掉生产必带 `reason: 'agent 未产生任何回答内容'`；
- 用 `capabilities.has(...)` 的实现声明代替真实可观测事实；
- S-J9 已指出断言对象错位却被默认驳回。

因此，人工终审不能只按当前分流表机械接受「只有三项未闭环」：S-J4/S-J5/S-J9 涉及报表口径与证据有效性，应重新分诊；S-J11 已随 P-M4 处理，不重复列为未修。

`buildFinishPayload` 是 `agent-runner.ts` 内局部辅助函数，并非可复用导出；本特性 spec 又禁止 tooling 深引 apps/web 内部模块。因而不能泛化要求“所有高风险契约都拉生产工厂”，否则会造成新的跨 app 耦合。

### 3.5 P1：用户成本还来自基线、前期提问和人工理解决策包

阶段 3B 多次逐级询问并逐步扩大到测试文件、本机索引和测试残留；ADR 初稿后因漏读持久化 schema 重写；36 条 US 混入实现步骤；双轴对 S-H6/P-M7 存在公开分歧，人工决策包却没有并列呈现两轴理由。

这些成本不能靠再增加状态字段解决，应靠范围、信息和停止规则减少。

### 3.6 P2：本特性还有独立的工程覆盖盲区

r1–r3 Standards 连续指出 `tooling/eval/**` 不在常规 `pnpm typecheck` 覆盖面内；真实 adapter 还存在测试未直接导入、改动后缺少专属类型与组合根加载证据的问题。本次反复出现的 `tsx` 临时探针与此直接相关。它属于该特性的交付命令和测试覆盖问题，**不应再转化成一层通用工作流门禁**。后续修复该特性时，应显式验证真实组合根导入与对应类型检查，不得以全仓 typecheck 的 PASS 推断这些文件已被覆盖。

## 4. 最终最小实施包

### 步骤 1：一次性修清确定性工具缺陷

**改动**

1. **finding 解析统一且只锚定标题行首**
   - 支持 `## S-H1` 与 `## [S-H1]`，仅匹配 Markdown 标题中紧跟井号的主编号，不扫标题中段、正文引用和示例。
   - seal、历史扫描、nextIds、scaffold-report、`--pending-ids`、`rereviewMissing`、qa-check 原文核对全部复用同一解析器。
   - `hasNoFinding` 只在 0 finding 时生效，并排除「无发现部分」等局部修饰语；不得让局部小节把真实发现吞掉。
2. **骨架按 changed 拆行**：同一 `reviewUnit` 中 changed 与 unchanged 断言分成独立复核行，保持与 `specReviewCoverageIssues` 同一语义。
3. **seal 写前保护**：先检查 `.source.json` 是否存在，再写 axes；已 `returned` 的轴被后续失败 seal 时不得降级覆盖。`startedAt` 不再用于计算审查时长；若未来允许调整字段语义，再改名为 `firstSealAttemptAt`。
4. **qa-run 错误可观测**：错误输出统一带 `[qa-run][ERROR]` 前缀；流程指引禁止用管道过滤后只读旧日志 exit，必须检查本次命令退出状态。

**验证**

- 本次 r1 脱敏原文应登记 24 条、17 条 Standards；r2 起点为 `S-H7 / S-J12 / P-M5 / P-W3 / P-X2`。
- r3 的「无新增审查发现（除 S-H7/S-H8/S-H9 外）」和正文引用不得产生假撞号。
- 混合 changed 骨架首次 seal 不再因 unchanged 被预填「变更成立」而失败。
- 重复 seal 已存在凭据时，axes 保持原 returned 状态。
- 重放全仓历史原文；若出现任一示例编号、说明标题或正文引用误建档，停止放宽解析，退回严格方括号并给出精确行号提示。

### 步骤 2：只读新鲜度预检 + 物理停手白名单

**改动**

1. acceptance 生成清单时记录 `evidenceTree` 与剔除 `## 交付验证` 后的 `qaPlanDigest`。
2. `checkSealability` 只读比较当前清单摘要，并要求存在同 tree 的完整 `gate-acceptance-*.log`；不一致报 `PACKAGE_INVALID`。
3. **不在 collect 内无条件重跑 acceptance**。它会覆写 `_qa/` 三个文件，而且含合法 `ASSERTION_BLOCKED` 的计划仍允许进入审查，不能一刀切阻塞。
4. `WAITING_HUMAN` 后仅允许：
   - 更新 qa-plan 的 `## 交付验证`；
   - 更新 review-report 的状态登记、人工裁决与范围说明，包括双轴分歧对照。
   禁止修改源码、测试、`## 执行记录`，禁止把未复审新发现标为「已修」。
5. 后台认领以 `.source.json` 和原文哈希为封存真源；axes 只作辅助指标。发现已存在凭据时禁止重派、禁止手改 `_qa/`。

**验证**

- 本例旧 acceptance 必须在双轴派发前被拦截。
- 带合法 `ASSERTION_BLOCKED` 但清单新鲜的计划不得被误阻断。
- 选择不再开 r4 后，不得新增由本流程自己造成的 `STALE_QA_ARTIFACTS/SUPERSEDED/FIX_UNVERIFIED`。
- 双轴存在 S-H6/P-M7 这类冲突时，人工决策包直接并列两轴结论和依据，不要求用户重读两份全文。

### 步骤 3：零代码规则与提示收口

1. **基线默认只读、一次聚合汇报**：无关既有红默认标注后继续。修改 git tracked 文件必须离开本特性另起任务；不改变 tracked 文件的本机环境恢复，如 `pnpm install --offline`，可在一次明确确认后执行，不为它额外切一张工单。
2. **测试假绿定级**：在 `code-review/SKILL.md` 明确“使用生产不存在事件或形状导致假绿”归 P-W/S-H。优先使用共享强类型契约和有出处的生产形状样本；不跨 app 强引内部构造器，不规定所有低风险测试都走真实工厂。
3. **需求与规格减法**：选项涉及生产事件、持久化、公共契约时先读实现再问人；删除实现步骤型 US；init 前检查断言是否互相矛盾、是否能证伪。
4. **保留一次一个决策的拷问方式**：当前 `grilling/SKILL.md:6-12` 明确要求一次一问并等待反馈。合并多题会降低交互次数，但属于另一项协议修改，不混入本批。先通过漏读事实减少问题数量。
5. **缩小交付与精简播报**：不把 fail-closed、真实 adapter、消融扩展一次性捆审；Advisor 只在设计冻结前寻找核心反例，截断/不可用/额度耗尽不自动重取；状态变化只写一行中文。

**停止条件**

- 若基线另起任务使净用户交互不降反升，回退该条规则表述并重新测量。
- 若强类型与样本约束仍不足以防止假绿，只为该高风险路径增加同模块契约测试，不泛化成全仓重型要求。
- 若人工终审新增漏检上升，停止对应减负规则，不以交互数下降作为成功。

### 步骤 4（独立实验）：修复继承失效后再考虑删除手填表

**先验证，不直接全面放宽**

1. 先用本特性 r1/r2/r3 快照构造脱敏 fixture，证明旧 acceptance 能被拦截后，再评估继承。
2. 仅对低风险 unit/integration 单元，在测试文件、静态导入闭包内实现源码、断言哈希均未变且当前测试覆盖通过时，允许继承；日志文件名改变或无关全局 tree 变化不应单独使继承归零。
3. 安全、权限、隐私、计费、`changed`、browser/api、非 PASS 永不降级。环境变量、运行时动态注入、动态 import 等无法静态排除的影响必须列入失效条件。
4. 用“只改实现、未改测试文件”的变异盲测验证任何应复审单元都不会被误继承。出现一例误继承，立即回退放宽，仅保留新鲜度预检。

**后续顺序**

- 继承修复证明有效后，再做删除手填 PASS 表的消融。
- `qa-run` 批执行仅在同类 Shell 返工再次出现时考虑；必须跳过同 tree、同 argv、exit 0 的日志，不支持 Shell 复合语法。当前九条命令虽 9/9 可直接 argv 执行，但只有一批约 35 秒属可避免返工，不是本次主要瓶颈。

## 5. 双方分歧的最终裁决

| 分歧 | 最终建议 | 理由 |
| --- | --- | --- |
| collect 无条件重跑 acceptance vs 只读预检 | **只读预检** | 避免覆写 `_qa/`、缺少 qa-run 门禁日志和合法 BLOCKED 死锁 |
| 放宽 reviewUnits 继承 | **先实验，暂不直接采用** | r1→r2 的 7 个失效单元证明潜在收益，但静态闭包不能覆盖所有运行时影响 |
| 生产内部 payload 工厂 vs 共享契约 | **共享强类型 + 有出处的生产形状；必要时同模块测试** | `buildFinishPayload` 是局部函数，深引会破坏既有模块边界 |
| 基线修复一律切任务 vs 本机环境豁免 | **tracked 文件修改切任务，本机环境恢复一次确认后可就地做** | 同时控制 scope 污染和切换成本 |
| TC 标题精确硬锁 | **否决** | 一个 `it()` 可合法覆盖多条原子断言，硬锁只会逼出机械拆测试；static 无关绑定可单独清理 |
| 哈希自动升强 | **否决** | 两轴均有 2 份同哈希候选，后到代理可回显他人 receipt |
| 合并无依赖问题一次多问 | **本批不采用** | 与当前 grilling 一次一问规则冲突；先减少事实型问题 |
| 立即建设交付批执行 | **低优暂缓** | 技术可行，但本例可避免成本只有一批约 35 秒，优先级远低于继承和工具 bug |

## 6. 发布验证与停止线

**工具回归**

- `node --test 'tooling/scripts/__tests__/*.test.mjs'` 全绿；安装模板与核心脚本保持同步。
- 全仓历史审查原文回放无新增误编号、误撞号、误无发现。
- r3 旧验收在派发前阻断；合法 BLOCKED 计划不误阻断。
- 重复 seal 不污染 returned axes；混合 changed 骨架不再首轮失败。

**效率轨**

- 用户决策次数、主 Agent 手工改表次数、重复交付批次数、无效首次 seal 次数分别记录，不混成一个“效率提升百分比”。
- 同类 fixture 比较继承前后的 Spec 实际核对单元数、工具调用和墙钟等待；不使用当前含义失真的 `startedAt` 计算审查耗时。
- 基线污染文件数、收口自造门禁错误数、并发覆盖次数必须下降。

**质量轨**

- r1 的 24 条发现完整进入登记和骨架。
- 只改实现未改测试的变异不得被误继承；人工终审新增漏检不得上升。
- 未修、修错、双轴分歧、弱来源和既有失败均如实呈现，不能为效率改写成完成。

优先复用本次转录、快照和日志做脱敏回放，不为每个假设都跑一场昂贵 dogfood。只有继承放宽、删除手填表和批执行这类可能改变协议或证据语义的改动，才需要独立 ADR 和同类真实任务对照。
