## 三、 候选故障假设验证与 Bad Case 诊断书

在 Phase 0 中，我们针对生产环境最常见的 3 大类候选故障进行了实地诊断与归因分析：

### Bad Case 1：重复调用同一失效工具，陷入盲目重试
* **现象**：在没有去重管道的系统中，当模型调用工具失败后，容易在第 2 轮、第 3 轮重复传入相同的错误参数（如反复查一个不存在的城市）。
* **复现与实验**：在 Case 3 中，模型连续发起两次 `web_search({ query: 'Next.js 15' })`。
* **现有防御效果**：
  - `tool-pipeline.ts` 的 `stableSerialize` 将参数哈希化，第 2 次调用在 `toolCache.get(cacheKey)` 处被瞬间拦截；
  - 成功避免了重复对第三方搜索引擎发送 HTTP 请求，节省了 API 费用并缩短了端到端耗时。
* **潜在风险与遗留项**：若模型每次在参数后微调一个无意义字符（如从 `'Next.js 15'` 变成 `'Next.js 15 '`），当前哈希缓存将无法识别语义重复，此问题将在 Phase 1 评测中作为边界样本持续监控。

---

### Bad Case 2：外部接口雪崩导致无意义 Token 消耗
* **现象**：第三方依赖服务宕机，若无熔断机制，Agent 将一直尝试重试直至步数打满（5 步全部耗尽）。
* **复现与实验**：在 Case 5 中模拟上游服务持续返回 500。
* **现有防御效果**：
  - 滑动连败计数器在累计 3 次失败后触发跳闸；
  - 相比无熔断设计，提前 1 轮终结了徒劳的调用，直接节省了约 25%~30% 的请求 Token 和等待耗时，并保证用户界面收到结构化收尾回答而非底层 500 堆栈错误。

---

### Bad Case 3：HTTP 同步长连接中断导致任务“人间蒸发”
* **现象**：对于长达数十秒的复杂 Agent 调研任务，若用户刷新页面或遇到网关 504 Gateway Timeout，前端无法再收到任何流式更新。
* **根本原因定位**：
  - 现有的 `agent-runner.ts` 执行完全依附于 Next.js API Route Handler 的单个同步 HTTP 连接；
  - 所有的中间会话状态（`ChainedMessageSession`）全部保存在 Node.js 内存堆中；
  - 数据库中虽有 `agent_runs` 表，但该表是在 `onFinish` 回调时才落盘的，属于**完成态账本**，不具备运行期快照特征。一旦连接中断或进程被 Kill，中间过程数据完全无法恢复。
* **下一步演进路线（Phase 2 核心动机）**：
  - 必须将长耗时 Agent 状态机剥离到后台 **BullMQ Worker** 异步执行；
  - 实现基于 PostgreSQL 的**节点级快照（Checkpointer）**，确保刷新后可通过 `taskId` 重新挂载与断点续跑。
