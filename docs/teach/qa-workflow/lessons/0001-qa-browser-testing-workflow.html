研发与真实浏览器真机测试闭环工作流实战教程

告别“单测全绿线上白屏”、“需求模糊瞎写返工”。本课程将系统拆解如何结合规格契约（Spec）、测试驱动开发（TDD）与真实 Chromium 浏览器自动化验收，打造高可靠的工程交付闭环。

🎯 学习目标：掌握 7 大阶段执行与排障定界 ⏱ 建议学习时长：15 分钟 📦 关联代码：AI-aggregation Monorepo

1 为什么必须建立这套工作流？

传统 AI 辅助开发的致命陷阱
  • 盲目直接写码：需求一句话，AI 改了 10 个文件后发现方向完全跑偏。
  • 单测假绿灯忽悠：纯内存 Node 虚拟机 mock 测通过，浏览器打开却白屏崩溃。
  • 环境故障乱改代码：上游大模型欠费 403，误以为自己代码写错而盲目重构。
  • PR 缺乏证据：提 PR 时无从知晓是否真正在前台跑通，代码审查靠猜。
闭环工作流的核心解法
  • 未对齐不写码：强制先盘问需求并产出规格合同（Spec）与架构决策（ADR）。
  • 真实浏览器真机验收：核心链路必须用真实 Chromium 逐条冒烟截屏落盘。
  • 探活与三层探针：网络与服务先探活，独立脚本隔离环境瞬态与代码缺陷。
  • 完整证据链沉淀：截图证据自动关联 PR，可信度闭环交付。

2 技能权限矩阵：命令到底由谁来触发？

许多新同学误以为“所有技能都要人手动敲”或“某些技能只有模型能用”。其实技能严格分为两类，分工非常明确：

开发者独占命令（模型被禁调）

配置了安全闸门，模型无法自主调用，必须由开发者在对话框显式敲入：

/grill-with-docs — 启动需求高压盘问
/to-spec — 锁定技术规格与契约
/implement — 授权开启 TDD 驱动编码
/grill-me — 轻量级逻辑盘问推演
💡 为什么？ 防止模型“自己提需求、自己写规格、自己通过”，产生失控的确认偏误。
通用协同技能（双向均可调用）

模型可在流程中自主调用，同时开发者随时可以手动调用：

ego-browser — 驱动真实 Chromium 浏览器与截图
qa-test-planner — 规划端到端测试用例
diagnosing-bugs — 科学故障定位与隔离探针
tdd — 红绿循环切片单测驱动
code-review / pr / retro
💡 提示： 日常开发想看页面随时敲 /ego-browser；想查 Bug 随时敲 /diagnosing-bugs。

核心产物辨析 01 /to-spec 产物

技术规格（Spec）和 PRD 需求文档、开发计划（Plan）到底有什么区别？

文档类型 回答的核心问题 主要读者 典型关注内容
需求文档 (PRD) “做给谁看、要什么商业/业务价值？” 产品经理、UI/UX、业务方 业务流程图、原型草图、用户价值、ROI
技术规格 (Spec) “系统的物理接缝与接口契约合同是什么？” 开发者、测试架构师、AI Agent 导出函数签名、数据 Schema、异常状态机、测试接缝
实现计划 (Plan) “第一步改哪、第二步加啥？” 执行编码的具体人员 操作步骤便签，用完即弃
本地结构澄清 02 /to-tickets 产物

为什么技能叫 /to-tickets，本地却只有 issues 文件夹？

因为当前仓库托管在 Gitee（无 GitHub CLI 工具），根据仓库顶层规范（docs/agents/issue-tracker.md），项目建立了本地的 Markdown Issue Tracker。 所有实现工单一题一文件编号存放在：
.scratch/<feature-slug>/issues/<NN>-<slug>.md（例如 01-agent-note-contract.md）。
本地只有 issues/ 目录，没有 tickets/ 目录，它们指代同一个工单体系。

测试原理辨析 03 /implement + TDD

TDD 中的“红灯”是故意写的反面教材或者错误例子吗？

❌ 错误理解： 红灯测试是故意写错参数、或者故意写反逻辑去试探报错。

✅ 真正原理： 红灯测试是一个 100% 正确、符合 Spec 规格、对未来功能提出合理预期的正面测试！

它之所以是“红灯（报错退出）”，仅仅是因为业务代码此时根本还没写（函数尚未定义或未实现）！先确认红灯，是为了证明这个测试具备真实的拦截能力，杜绝写出“代码写错也依然能过”的无效测试。随后编写最简代码让它变绿，再进行重构。

代码把关辨析 04 code-review

“规范轴”是不是日常说的 Code Review？为什么还要“需求轴”？

完全正确！规范轴就是大家最熟悉的传统 Code Review（检查有无 any 破坏类型安全、有无内存泄漏、有无硬编码凭证、有无违反 DESIGN.md）。
但单有规范轴存在巨大盲区：一段代码可以写得极其优雅、单测 100% 绿灯，但压根漏掉了 Spec 要求的异常降级，甚至夹带了私货！
需求轴（Spec 轴） 专门拿代码对照 spec.md“对账”，确认业务承诺被精准兑现、没有私自扩范围。规范轴保底线，需求轴保方向。

4 真实浏览器真机验收：执行细节与防踩坑心法

执行全流程：从就绪到 PASS 回填

Step 1：端口探活 curl 探活 3030 返回 200，未返回先启动 pnpm dev:web。
Step 2：就绪锚点 等待输入框渲染可交互。严禁 networkidle 防 SSR 水合假死。
Step 3：真机交互 按 qa-plan.md 逐条点击输入，抓取操作帧截图保存到 .scratch。
Step 4：PASS 回填 在 qa-plan.md 的「## 执行记录」追加通过结论与截图名。

时间盒成本控制：什么时候用 ego-browser？什么时候用 Playwright？

工具 运行机制 速度与成本 适用场景
ego-browser 交互验收 大模型逐帧观察截图、推断交互、模拟操作 1~3分钟/条，消耗大模型多模态 Token 本次新改动的核心链路首次验收、人工接管登录、抓取 PR 截图证据
Playwright 脚本 (test:e2e) Node.js 进程极速执行预置确定性测试脚本 秒级完成，0 Token 消耗 全站历史存量功能的防退化回归、CI 流水线常规把关

📌 时间盒纪律：单次 ego-browser 验收用例严格控制在 3~5 条 P0 冒烟 内，时间盒上限 15 分钟。超时立即停下交互，改用隔离探针排障。

排障心法：遇到上游报错时的“三层隔离探针链”

在浏览器中遇到大模型上游返回错误（如 No output generated）时，切忌直接删改本地业务代码！先建立临时脚本 probe.mts 逐层排查：

一层：裸 curl 直连 直连官方域名，排查欠费 403 或本地代理阻断。
二层：极简官方 SDK 调用官方最简单测，排查 API Key 凭证有效性。
三层：本地适配器 前两层皆通，方可接入本地 Adapter 定位代码逻辑。

5 跨会话无缝交接契约：新会话提示词模板

开新会话接着做任务时，切忌只说“接着做吧”。套用以下标准话术，模型可瞬间读取磁盘契约恢复上下文：

模板 A：从规格到编码实现
我刚才完成了 <feature> 的规格与测试规划。请先阅读 .scratch/<feature>/spec.md 和 .scratch/<feature>/qa-plan.md 熟悉契约，然后直接执行 /implement 开启 TDD 编码实现。
模板 B：从编码到真机浏览器验收
<feature> 的业务代码和单测已完成。请阅读 .scratch/<feature>/qa-plan.md，执行阶段 5 真实浏览器验收。确保先通过 curl 探活 3030 端口，使用 ego-browser 逐条执行 P0 用例，将截图存入 .scratch/<feature>/screenshots/ 并回填执行记录。
模板 C：中途接力未完成的浏览器验收
请阅读 .scratch/<feature>/qa-plan.md，重点查看末尾的 ## 执行记录，接力执行尚未 PASS 的用例，遇到问题调用 diagnosing-bugs 进行自愈排查。
