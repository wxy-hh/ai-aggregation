## Problem Statement

平台处于内测阶段、公网入口已开放，但认证链路存在一批可被直接利用的缺口：

- 登录/注册/忘记密码等认证接口没有任何频次限制和失败锁定，账密可被在线爆破，注册接口可被批量调用刷取免费额度；
- 图像/视频代理接口是无鉴权的任意 URL 转发，可被用于攻击内网（SSRF）、充当免费流量代理、或在平台域名下投放钓鱼内容；
- refresh token 与密码重置 token 在数据库中明文存储，数据库一旦泄露，所有 30 天有效期的会话可被直接接管；
- 被禁用的用户仍可通过微信/QQ 扫码拿到完整会话；
- 登出接口支持 GET 方法，第三方页面可强制任意访客登出；
- 登录凭证（accessToken）持久化在 localStorage，任何 XSS 都可静默窃取；
- 「忘记密码」是假流程：服务端生成了重置令牌但根本没有邮件通道，用户永远收不到邮件，账密用户丢密码即丢号（连同额度与历史记录）。

同时存在一批持续误导后来者的卫生问题：文档仍以 NextAuth 心智模型描述实际为零引用的配置、匿名验收脚本按旧的 3000 额度断言（现值 20000，脚本跑必败）、过期 token 永久堆积无清理。

## Solution

在内测窗口期（无真实用户、破坏性变更成本最低）对现有自研认证链路做一次集中加固，不换认证框架：

1. 堵死可被直接利用的口子：代理接口加白名单、认证接口加限流与失败锁定、token 哈希存库、禁用用户全链路拦截、登出收敛为 POST、登录错误响应不再泄露内部细节；
2. 登录凭证从 localStorage 迁移到内存，页面刷新后通过现有 refresh 通道静默恢复会话；
3. 补齐邮件通道（阿里云邮件推送），让忘记密码真正可用，注册支持选填邮箱、个人中心支持绑定邮箱；
4. 限流器按路由性质分层：认证类路由 Redis 故障时拒绝服务（fail-closed），业务类路由放行但记录告警（fail-open）；
5. 还清卫生债：过期 token 每日清理、文档与验收脚本对齐现状、删除死代码。

明确不做：匿名模式防刷收紧（匿名是内测临时功能，终态删除，不值得投入）。

## User Stories

1. 作为平台运营者，我希望登录接口有频次限制和失败锁定，以便攻击者无法在线爆破用户密码。
2. 作为平台运营者，我希望注册接口有频次限制，以便攻击者无法批量注册账号刷取免费额度。
3. 作为平台运营者，我希望忘记密码/重置密码接口有频次限制，以便重置令牌无法被暴力枚举。
4. 作为平台运营者，我希望图像/视频代理只转发白名单域名的资源，以便代理接口不能被用来攻击内网或充当开放代理。
5. 作为平台运营者，我希望代理接口不透传 `text/html` 等危险内容类型，以便攻击者无法在我的域名下投放钓鱼页面。
6. 作为平台运营者，我希望 refresh token 在数据库中以哈希形式存储，以便数据库泄露时攻击者无法直接接管用户会话。
7. 作为平台运营者，我希望密码重置令牌同样以哈希形式存储，以便数据库泄露时无法被直接用于改密。
8. 作为平台运营者，我希望被禁用的用户在任何登录入口（账密/微信/QQ）都无法获得会话，以便封禁是彻底且一致的。
9. 作为平台运营者，我希望登出接口只接受 POST，以便第三方页面无法通过图片标签强制我的用户登出。
10. 作为平台运营者，我希望登录/注册失败响应不包含数据库等内部错误细节，以便攻击者无法借此侦察系统内部结构。
11. 作为平台运营者，我希望认证类接口在限流设施故障时拒绝服务，以便安全防线不会在基础设施抖动时自动消失。
12. 作为平台运营者，我希望业务类接口在限流设施故障时仍能服务（有数据库层配额兜底），以便 Redis 抖动不影响正常用户使用产品。
13. 作为平台运营者，我希望限流器故障时产生告警日志而非静默吞掉异常，以便我能及时发现限流防线处于失效状态。
14. 作为普通用户，我希望我的登录凭证不持久化在浏览器磁盘上，以便常见 XSS 攻击无法静默窃取我的身份。
15. 作为普通用户，我希望刷新页面后我的登录状态能自动恢复，以便凭证内存化不影响我的正常使用体验。
16. 作为普通用户，我希望忘记密码时真的能收到重置邮件，以便我丢密码后能找回账号和里面的额度。
17. 作为普通用户，我希望注册时邮箱是选填而非必填，以便我能以最低摩擦完成注册。
18. 作为普通用户，我希望注册时填写的邮箱经过验证码确认归属，以便我的账号找回通道确实指向我自己的邮箱。
19. 作为普通用户，我希望能在个人中心事后绑定邮箱，以便注册时没填邮箱也能事后补上找回通道。
20. 作为普通用户，我希望绑定/更换邮箱时需要验证码确认，以便他人无法把我的账号绑到别人的邮箱上。
21. 作为普通用户，我希望未绑定邮箱的账号在忘记密码时得到明确指引（用微信/QQ 登录或重新注册），以便我不会空等一封永远不会来的邮件。
22. 作为普通用户，我希望连续输错密码后收到明确的锁定提示和解锁时间，以便我理解为什么暂时无法登录。
23. 作为微信/QQ 登录用户，我希望第三方登录流程不受本次加固影响，以便我的使用体验保持现状。
24. 作为匿名访客，我希望内测期间的匿名体验链路不受本次加固影响，以便我能继续无摩擦地体验产品并反馈问题。
25. 作为管理员，我希望我的超管账号继续通过账密登录管理后台，以便管理方式不需要改变。
26. 作为管理员，我希望管理后台登录入口同样受限流和锁定保护，以便后台入口不被爆破。
27. 作为开发者，我希望过期的 refresh token 被每日自动清理，以便认证表不会无限膨胀。
28. 作为开发者，我希望环境变量示例和部署文档准确描述自研认证方案，以便我不会按 NextAuth 的心智模型误配系统。
29. 作为开发者，我希望匿名验收脚本的断言与当前额度常量一致，以便它能作为有效的回归验收手段。
30. 作为开发者，我希望死代码（已无调用方的认证辅助模块）被清除，以便代码库不传递错误的架构信号。
31. 作为开发者，我希望种子脚本不在仓库中硬编码测试密码，以便开发设施不成为泄露源。
32. 作为开发者，我希望限流器的 fail-open/fail-closed 行为有单源的决策表测试，以便行为演进时被测试守护而非靠人肉同步。
33. 作为平台运营者，我希望整个加固在内测窗口完成（token 哈希切换导致现有会话全部失效是可以接受的），以便不留兼容包袱。
34. 作为平台运营者，我希望三入口（账密/微信/QQ）长期并存，以便不同偏好的用户都有合适的登录方式。
35. 作为平台运营者，我希望匿名模式的防刷问题不做投入（该功能终态删除），以便加固资源集中用在长期存在的链路上。

## Implementation Decisions

### 总体架构

- **保留自研认证方案**（HS256 JWT + bcrypt + 数据库 refresh token + httpOnly cookie），不迁移 Auth.js/NextAuth。理由：微信扫码、匿名设备指纹、配额体系均深度耦合自研链路，现有问题全部位于加固层而非架构层。
- **登录方式终态为三入口并存**：账密、微信扫码、QQ OAuth。
- **匿名模式维持现状**：内测临时收集反馈用，终态删除；本轮不做任何匿名防刷收紧。

### A. 代理接口收口（SSRF 修复）

- 图像/视频代理接口增加**目标域名白名单**：仅允许平台自身使用的对象存储/CDN 域名（OSS、MinIO 及上游生成结果域名，实施时以环境变量配置维护）。
- 强制仅允许 `https` 协议；拦截内网地址段（含云元数据地址）。
- 透传的 Content-Type 收敛为媒体白名单（`image/*`、`video/*`），其余一律拒绝；响应不再无条件声明公开缓存。
- 代理接口仍不需要用户登录（公开资源访问场景），但必须带白名单约束。
- **实现备注**：白名单为 `image/*`（`image/svg+xml` 除外）、`video/*` 与 `application/octet-stream`（部分上游以二进制流返回生成结果）；额外拒绝 `image/svg+xml` 是因为 SVG 可内嵌脚本、在平台域名下即构成存储型 XSS；上游缺失 `Content-Type` 时不拦截，回退为路由默认类型（图片 `image/png`、视频 `video/mp4`），响应固定写入 `X-Content-Type-Options: nosniff`，因此回退类型不会被浏览器嗅探执行。

### B. 认证接口限流与登录锁定

- 以下接口全部接入限流器（复用现有 RateLimiter + Redis 设施）：登录、注册、忘记密码、重置密码（匿名建号接口现有限流保留）。
- 登录增加**失败计数 + 渐进锁定**：失败计数存 Redis（不改动数据库 schema），同一账号连续失败达到阈值后锁定一段时间并返回明确的锁定提示与剩余时间；登录成功清零计数。
- **实现备注**：锁定期内的尝试只拒绝（423 + 剩余分钟数），**不累计失败、不延长锁定**——否则攻击者周期性尝试即可把账号永久锁死（锁定 DoS）；锁定期满后再次失败才从已有计数继续累进翻倍（跨锁定周期仍渐进，上限 24 小时）。阈值：连续失败 5 次锁 15 分钟，每再失败一次翻倍。
- 限流器新增 **fail-open / fail-closed 模式参数**：
  - 认证类接口使用 fail-closed：Redis 异常或超时时拒绝请求（503），安全边界不设「故障自动放行」；
  - 业务类接口维持 fail-open，但异常必须记 warn 级日志，不再静默吞掉；
  - 限流器内部超时从 2.5s 收紧至 1s。
- 登录/注册失败响应收敛为通用文案，不再把底层异常 message 透传给客户端。

### C. Token 存储加固

- refresh token 落库前计算 SHA-256 摘要，库中只存摘要；校验时先哈希再比对。
- 密码重置令牌（`reset:` 前缀）同样只存摘要。
- 切换时存量 token 全部失效——内测阶段可接受，不做双读兼容。
- 新增 Worker 侧 BullMQ repeatable job：每日清理已过期的 refresh token 记录，不引入新的调度设施。

### D. 会话与禁用一致性

- 微信/QQ OAuth 回调在命中已有第三方账号绑定后、签发会话前，补充用户状态检查：被禁用用户拒绝签发并给出明确提示，与账密登录行为对齐。
- 登出接口仅保留 POST 方法，移除 GET 处理。

### E. 前端凭证内存化

- accessToken 从持久化存储中移除，仅保存在内存；持久化层不再序列化 accessToken。
- 页面刷新后复用现有初始化流程：先通过 httpOnly cookie 中的 refresh token 静默换取新 accessToken，再进入就绪态；该路径已存在，本次将其从「冷启动兜底」变为「每次必走」。
- 用户基本信息对象（含额度快照）的持久化维持现状。
- 所有 API 请求必须统一走带 401 自动刷新重试的请求封装，不得绕开。

### F. 邮件通道与忘记密码补完

- 接入**阿里云邮件推送**，封装平台级「发送验证码」能力，供注册验证、绑定邮箱两处复用（忘记密码走重置链接，不发验证码）。
- 验证码存储复用现有 token 表的前缀模式，新增 `verify:` 前缀，与 `reset:` 一致只存摘要、限时有效、一次性使用。
- 注册页：邮箱选填；填写则须通过验证码校验后才计入账号。
- 个人中心：新增「绑定/更换邮箱」，流程为输入邮箱 → 验证码确认 → 生效。
- 忘记密码：真正发送重置邮件；对已注册但未绑定邮箱的账号，提交后提示改用微信/QQ 登录或重新注册（对外响应仍保持防枚举的恒定文案口径，引导信息不泄露账号是否存在）。
- 邮件服务商凭证通过环境变量配置，文档补充配置指引。
- **实现备注**：`send-code` 接口的 `purpose` 只保留 `register` / `bind`——`reset` 用途发出的验证码没有任何消费点（忘记密码全程走邮件里的重置链接，重置令牌仍复用 `reset:` 前缀存库），故直接删除而非保留死路径。
- **实现备注**：验证码实际存 Redis（键 `verify:<purpose>:<email>`、值只存 SHA-256 摘要、TTL 10 分钟、验证通过即删），未走「复用 RefreshToken 表加前缀」的方案——注册场景用户尚不存在，无法挂 `userId` 外键，Redis 键天然按「用途 + 邮箱」寻址，且天然带 TTL 与一次性删除语义。

### G. 卫生项

- 清除环境变量示例与部署文档中的 NextAuth 残留描述，统一为自研认证的心智模型。
- 更新匿名访问需求的覆盖矩阵文档中已过时的现状描述（原「可选用户标识」机制已全量改为强制鉴权）。
- 修正匿名验收脚本的额度断言（3000 → 与当前常量 20000 对齐）。
- 删除已无调用方的认证辅助模块。
- 种子脚本的测试账号密码改为环境变量驱动，缺省时随机生成并打印，不再硬编码。

### 明确否决的方案（来自拷问记录）

- 迁移 Auth.js/NextAuth —— 微信扫码与匿名模式适配成本高，问题不在架构层；
- accessToken 改 httpOnly cookie —— 会引入全站 CSRF 防护需求，当前阶段负收益；
- 匿名额度降额/验证码/加强 IP 限流 —— 临时功能不值得投入；
- 账密入口下线或降为隐藏入口 —— 已拍板三入口并存；
- 为忘记密码新建独立数据表 —— 复用现有 token 表前缀模式即可。

## Testing Decisions

### 好测试的标准

只断言外部可观察行为：HTTP 状态码与响应体、Set-Cookie 属性、数据库写入内容（哈希后的摘要而非明文）、发出的邮件/验证码参数、限流命中与锁定提示、持久化存储中不再出现的字段。不断言内部函数调用、不复制被测对象的决策表（遵循 ADR-0003「接口即测试面」）。

### 测试接缝（均为现有接缝，不新增）

| 接缝 | 覆盖内容 | 先例 |
|---|---|---|
| API 路由测试（vitest，路由文件旁 `route.test.ts`，mock `@repo/db`） | 登录限流与渐进锁定、注册/忘记密码/重置密码限流、token 哈希落库与校验、OAuth 禁用拒绝、登出仅 POST、错误文案收敛、代理白名单放行/拦截矩阵 | `app/api/video/route.test.ts`、`app/api/internal/billing/reconcile/route.test.ts`、`app/api/chat/_lib/chat-handler.test.ts` |
| 限流器模块测试（`packages/shared`，决策表单源） | fail-open/fail-closed 两模式在 Redis 正常/异常/超时下的行为矩阵、1s 超时 | ADR-0003 的决策表单源化模式（`packages/db/src/__tests__/billing/quota-session.test.ts`） |
| 代理白名单判定纯函数测试 | 域名白名单、协议拦截、内网地址段拦截、Content-Type 白名单 | 现有纯函数测试惯例（如 `lib/device-fingerprint.test.ts`） |
| auth-store 测试 | accessToken 不再入持久化、刷新后静默恢复会话、401 重试路径不回归 | 现有 `stores/auth-store.test.ts` |
| HTTP 验收脚本（`scripts/`） | 扩展匿名验收脚本模式，覆盖：限流触发、锁定提示、登出 GET 拒绝、禁用用户 OAuth/账密拒绝；修正额度断言 | 现有 `scripts/test-anonymous-access.py` |
| Playwright E2E（仅关键链路） | 登录 → 刷新页面会话保持；忘记密码 → 收到邮件（测试收件箱）→ 重置 → 新密码登录 | 现有 `apps/web/e2e/*.spec.ts` |

> **实现备注**：Playwright E2E 两条链路**未实施**（需要真实邮件通道与可重复的测试收件箱，属真实环境依赖），留待内测部署后补；本轮对应的回归守护落在路由测试（vitest）与 HTTP 验收脚本上。

### 邮件通道的测试方式

发送层以可替换适配器实现，路由测试中断言「向适配器提交了正确的收件人与验证码」；真实阿里云投递不在单测内验证，由验收脚本与内测人工验证覆盖。

## Out of Scope

- 匿名模式的任何防刷收紧（临时功能，终态删除）；
- 认证框架迁移（Auth.js/NextAuth）；
- 邮箱验证码作为独立登录方式、手机号登录、2FA；
- accessToken 的 httpOnly cookie 化及配套 CSRF 体系；
- 会话管理 UI（已登录设备列表、远程踢下线）、登录审计日志模型化；
- 第三方平台 token（微信/QQ access_token）落库加密；
- CSP 与系统化 XSS 防护建设（本轮仅消除凭证持久化这一个面）；
- 生产级告警通道建设（本轮只保证 warn 日志落地）；
- 配额体系本身的调整（额度常量、扣费逻辑均不动）。

## Further Notes

- **切换代价**：token 哈希存库上线即全部现有会话失效，内测阶段可接受，需在部署说明中注明。
- **运维预案**：认证接口 fail-closed 后，Redis 长时间故障将导致无法登录；运维手册需说明此时可通过临时切换限流模式环境变量应急放行。
- **文档债**：本次同步更新部署文档、匿名需求覆盖矩阵、验收脚本；后续新增认证相关 ADR（建议至少一篇：token 哈希与限流分层决策）。
- **执行顺序**：限流器分层（支撑认证接口以 fail-closed 接入）→ A/B 安全加固 → E 前端内存化 → F 邮件通道 → G 卫生项；A、E、F 之间无依赖可并行。
