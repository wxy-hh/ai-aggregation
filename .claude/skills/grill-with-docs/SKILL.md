先调用 `grilling`，再调用 `domain-modeling`，逐项澄清业务边界和真实取舍。未达到共同理解前不得开始实现。
- 保留 `grilling` 一次一问的拷问协议（不合并多题提问），先通过查清事实减少问题数量：凡候选选项涉及生产事件、持久化 schema 或公共契约，必须先查阅对应实现与 schema 再向用户提问（先读实现再问人），不凭猜测出题。

## 领域产物

- 领域术语默认只更新 `GLOSSARY.md`，不默认同步 `CONTEXT.md`；只有用户明确要求同步稳定架构背景时才更新后者。
- ADR 只在难以逆转、缺乏背景会令人意外且存在真实取舍时创建。讨论结束时直接完成 ADR 判断和必要落盘，不把补 ADR 与 `/to-spec` 并列为两个“下一步建议”。

## 推翻既有决策

推荐项会改变既有默认值、ADR 或评测结论时，题干先引用原决策与证据路径（如 ADR、评测报告），每个选项都写出代价，不只写优势。用户确认后，ADR 写明取代了哪项决策及依据。推荐理由涉及质量或性能收益时，说明需要什么效果证据（例如可复现的对照评测）；给不出时按机制描述记入共识，不写成已证实的收益。

## 阶段收口（必须执行）

讨论与产物完成后，不得只输出“下一步建议 1/2/3”。统一报告：

- **当前已完成阶段**：阶段 1 需求对齐（若核心问题仍未收敛则不得声称完成）；
- **车道及理由**：快车道（文案、样式、非核心小修）／标准车道（独立功能，涉及模块少，串行可完成）／慢车道（跨多模块的复杂业务或大功能，或需要并行调度多个实现子代理），同时列出核心链路判定；
- **本阶段产物**：实际更新的 `GLOSSARY.md`、ADR 路径（确有 trade-off 时）及已确认的决策；
- **建议下一步：`/to-spec`**（快车道为 `/implement`），只写这一个命令。
